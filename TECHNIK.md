# Ratsatlas Köln – Technik

Technische Beschreibung von Pipeline, Seite und Betrieb. Worum es inhaltlich geht, steht in der [README](README.md); Auftrag und Entscheidungen stehen in [CLAUDE.md](CLAUDE.md).

## Aufbau des Repositorys

- `pipeline/` – Abruf (`abruf.py` Abrufpolitik, `sessionnet.py` Adapter für die Kölner OParl-API), Geodaten (`geodaten.py`), Aufbereitung (`build.py`), Geokodierung (`geocode.py`, `geo.py`, `plans.py`), Akteure (`actors.py`), Themen (`topics.py`), Prozessschritte (`process.py`), Export (`export.py`, `publish.py`), Datenpaket (`paket.py`), Seiten (`seo.py`, `gebietsseiten.py`, `begriffsseite.py`, `rssseite.py`, `technikseite.py`), Kartenkacheln (`kacheln/`). Bonner Zusatzthemen (Haushalt, Themenseiten, Baustellen, Soll-Modell, Ratsassistent u. a.) bleiben im Code, sind aber über `config.ZUSATZTHEMEN` abgeschaltet.
- `site/` – statische Seite (Leaflet, `app.js`, `timeline.js`, `tour.js`); Elemente der Zusatzthemen tragen `data-funktion` und bleiben ausgeblendet.
- `data/geo/` – Kölner Stadtteile, Stadtbezirke, Straßen- und Hausnummernverzeichnis (abgeleitet, dl-de/zero 2.0); `data/LICENSE-DATA.md`. Rohdaten (`data/raw/`) und Exporte (`data/export/`) sind nicht versioniert.
- `explore/` – Exploration (Phase 1): Messskripte für die OParl-API, Geodaten-Katalog, Anfrage an die Stadt.
- `inventur/` – Inventur der Bonner Kopie und Berichte der Phasen.
- `tests/` – Tests mit synthetischen Daten und einem lokalen OParl-Testserver; `tools/` – Testdaten, Seite zusammenstellen, WCAG-Prüfung.
- `.github/workflows/` – aktive Workflows; `.github/workflows-inaktiv/` – Bonner Workflows (laufen nicht).

## Pipeline

```bash
pip install -r requirements.txt
python -m pipeline fetch      # Abruf (gesperrt ohne RATSATLAS_STADT_INFORMIERT=ja; nur 23–1 Uhr)
python -m pipeline build      # SQLite data/build/allris.sqlite, Geokodierung, Akteure
python -m pipeline export     # data/export/koeln/, Audits, Stichprobe je Methode
python -m pipeline kontext    # Kennzahlen je Stadtteil, Flächen und Punkte (aus data/kontext/)
python -m pipeline ebenen     # Kartenebenen aus data/ebenen/ und export/koeln/ebenen.json
python -m pipeline package    # data/export/ratsatlas-koeln-export.zip
python -m pipeline kontext-ausschnitte   # einmalig: Zensus, BORIS, Klima, Überschwemmung, Kitas, Schulen, Haltestellen (Land, Bund)
python -m pipeline ebenen-laden          # einmalig: weitere Ebenen (Stadt, Land); je Datensatz höchstens 3 Anfragen
python -m pipeline bplan-koeln           # Bebauungspläne aus der OGC-API Bauleitplanung NRW
python -m pipeline geo-koeln  # Geodaten neu ableiten (lädt Zip-Dateien von offenedaten-koeln.de, falls nicht in data/raw/geo)
python -m pipeline strukturdaten-abruf   # nur auf Freigabe (STRUKTURDATEN_ABRUF=ja, RATSATLAS_KONTAKT); höchstens 7 Anfragen
python -m pipeline strukturdaten         # ohne Netz: Zwischenspeicher → data/strukturdaten/, mit Raumabgleich
```

| Schritt | Ergebnis |
|---|---|
| `fetch` | Rohdaten im Bonner Format in `data/raw/`: `papers.jsonl`, `organizations.json`, `meetings.json` (und `meetings_roh.jsonl` mit TOPs), `legislative_terms.json`, `beratungen.jsonl` (Beratung → Sitzung und TOP, aus den Sitzungen abgeleitet); Zustand `zustand_abruf.json` (Zeitpunkte, Fortsetzungen, Zähler `sperre_verdacht` und `listenfehler`, `letzter_abbruch`, `nicht_vor` aus einem Retry-After); Abrufstatistik `data/export/abrufstatistik.tsv`; `STAND.json` mit Zeitpunkten, `abruf_fehler`, `abruf_uebersprungen` oder `abruf_hinweis` (ein vollständiger Lauf entfernt alle drei) und `abruf_warnungen` (Nebenlisten, siehe unten) |
| `build` | Tabellen Vorlage, Beratung, Sitzung, Tagesordnungspunkt, Organisation, Ort, Ortsbezug (mit Stufe, Methode, Konfidenz, Fundstelle), Einreichende, Zuständigkeit |
| `export` | je Stadtteil, Stadtbezirk und Jahr ohne Ortsbezug; `index.json`, `suche.json`, `zeit.json`, `prozesse.json`, Feeds, Kalender, GeoJSON, DCAT; stadtweite Audits `audit_*.tsv` und `stichprobe_geokodierung.tsv` (veröffentlicht nur im Datenpaket, nicht als lose Dateien auf der Seite; `tools/seite_bauen.py`, `NUR_IM_PAKET`) |
| `seo` (über `tools/seite_bauen.py`) | Gebiets-, Begriffs-, Feed- und Technikseite, `robots.txt`, `sitemap.xml`, absolute Adressen aus `SITE_URL`; Texte abgeschalteter Funktionen entfernt (`seo.ohne_abgeschaltete`, siehe unten) |

Unerwartete Feldformen (Runde 18): `build` gleicht die Vorlagen beim Einlesen an (`build.einlesen`, `data/raw` bleibt unverändert): listenwertige OParl-Felder (`consultation`, `location`, `auxiliaryFile`, `keyword`, `underDirectionOf`, `originator*`, Beziehungen; in Beratungen `organization`, `keyword`) als einzelnes Objekt werden zur Liste, `null` zur leeren Liste, in `consultation` und `location` zählen nur Objekte mit Kennung, in Listen von Adressen (Beziehungen, `originator*`, `underDirectionOf`, `relatedPaper`; in Beratungen `organization`) zählt ein eingebettetes Objekt mit seiner `id`, Einträge ohne Kennung fallen heraus, ein `mainFile`, das kein Objekt ist, gilt als fehlend, `paperType` null gilt als leere Vorlagenart und eine Vorlagenart in anderer Form (Liste, Objekt) als Text aus ihren Zeichenkettenteilen, damit die Regel für Eingaben weiter greift; sie gilt zudem als nicht erkennbare Vorlagenart, also ohne Hauskoordinate (Tabelle `paper_type_other_form`, Entscheidung 10.11.2026; alles gezählt im Log von `build`). Vorlagen ohne `reference` (fehlend, null, leer) oder mit einer `reference`, die keine Zeichenkette ist, lässt `build` aus, ohne eine Nummer zu erfinden, mit Zählung je Grund im Log (`n Vorlagen ohne Drucksachennummer ausgelassen`, `n Vorlagen mit Drucksachennummer in unerwarteter Form ausgelassen`), in der Tabelle `skipped_paper` (`reason`) und als Zeilen der Ausgabe von `check`. Ebenso ausgelassen werden Vorlagen, die die Stadt als gelöscht meldet (`deleted: true`; Grund `gelöscht`, Zeile `n Vorlagen als gelöscht gemeldet (OParl deleted) ausgelassen`; Prüfung r19b), wenn es die Kennung nicht auch ohne Löschvermerk gibt: Ihre Art ist unbekannt, und vorher verloren die mit ihnen verbundenen Vorlagen die Sperre. Für den Datenschutz bleiben ausgelassene Vorlagen Teil der Regel: Ihre Kennungen gehören zur Startmenge ohne Hauskoordinate (ohne Drucksachennummer gibt es ohnehin keine Erlaubnis), ihre Beziehungen stehen in `paper_relation`, ihr `relatedPaper` in `paper_related`, die Kennungen ihrer Ortsangaben in `skipped_location` (der Export zeigt sie nicht, weil die Vorlage fehlt). So bekommt eine Beantwortung oder Stellungnahme zu einer Eingabe oder Einwohneranfrage ohne Drucksachennummer weder im Aufbau noch nach `check.erlaubnis` eine Hauskoordinate, gleich auf welcher Seite die Beziehung steht; ebenso blendet `maske.aus_db` die Hausnummer in ihrem Titel aus, und `volltext.einwohner_kette` verortet sie nicht aus dem Volltext. Ratsfraktionen und -gruppen führt Köln in der Klasse (`classification`) „Fraktionen und Gruppen“ (Stufe 3, `organizationType` fehlt); `actors.RAT_CLASSES` nimmt sie neben den Bonner Werten auf, „Sachkundige Bürgerinnen und Bürger“ in derselben Klasse passt auf kein Muster einer Fraktion und wird nie zugeordnet.

### Abrufpolitik (CLAUDE.md 5.1)

`pipeline/abruf.py`: eine Verbindung, mindestens 2 s Abstand (`RATSATLAS_ABSTAND`, auch vor der ersten Anfrage eines Prozesses), nur im Zeitfenster 23–1 Uhr Ortszeit (`RATSATLAS_ZEITFENSTER`; laut mandari die Vorgabe der Stadt, ohne Quelle der Stadt; geprüft vor jedem Versuch und nach dem Warten auf den Abstand noch einmal unmittelbar vor dem Senden), nach 429 und 5xx Pausen von 1 min bis 3 h (`Retry-After` als Sekunden oder HTTP-Datum wird eingehalten), sofortiger Abbruch bei 401/403/404. Eine Pause muss vor dem Ende des laufenden Zeitfensters enden (gerechnet in UTC, auch über eine Zeitumstellung); sonst, und wenn `Retry-After` länger als die längste Pause oder unlesbar ist, gibt der Abruf sofort auf („aufgegeben“), statt in einer späteren Nacht weiterzumachen. Ein solcher `Retry-After` gilt über die Nacht hinaus: Bis zu seinem Ablauf steht `nicht_vor` im Zustand und jeder Lauf wird übersprungen (höchstens 30 Tage; unlesbar 7 Tage; mehr als 12 Ziffern gelten als unendlich, also 30 Tage). Lokal (ohne Freigabe, Zeitfenster, Mindestabstand, 12-Stunden-Regel und `nicht_vor`) sind nur `http://127.0.0.1`, `http://localhost` und `http://[::1]` (Prüfung des Hosts, nicht des Anfangs der Adresse). Zeitüberschreitung, Verbindungsabbruch und abgeschnittene oder unlesbare Antworten (`http.client.HTTPException`, z. B. weniger Bytes als `Content-Length`) gelten als mögliche Sperre: Abbruch ohne Wiederholung, ebenso andere TLS-Fehler (unerwartetes Ende oder Reset im Handshake). Scheitert dagegen die Zertifikatsprüfung (`CERTIFICATE_VERIFY_FAILED`), ist das vermutlich eine Einstellung der Ausführungsumgebung (CA eines Proxys; ein Zertifikat der Gegenseite oder eine Sperrseite ist nicht ausgeschlossen): Abbruch der Art `tls` ohne Wiederholung, Warnung im Workflow-Log, gezählt als Fehler und nicht als Anfrage (die HTTP-Anfrage wurde nicht gesendet), keine Nacht mit möglicher Sperre; die 12-Stunden-Regel gilt (`letzter_abbruch`), Nächte mit `tls` zählt `tlsfehler`, nach drei Nächten ohne vollständigen Lauf dazwischen sieben Tage Pause. Eine Antwort, die kein JSON ist (auch zu tief verschachtelt), gilt wie 429/5xx. Gültiges JSON in unerwarteter Form (kein Objekt, Body ohne Listen, Listenseite ohne `data` oder mit einem nicht leeren `links`, das kein Objekt ist) bricht nach einer Anfrage ohne Wiederholung ab („unlesbar“); ein leeres `links` oder `links.next` (`null`, `""`, `[]`, `{}`; SessionNet ist in PHP geschrieben) gilt als Ende der Liste. Ungültige Adressen (Zeichen außerhalb von ASCII, ein anderes Schema als http oder https, kein Host, ungültiger Port, Leerzeichen) werden nicht gesendet und nicht gezählt; der Öffner kennt nur http und https (keine Handler für FTP, Dateien und `data:`). Andere Fehler vor dem Senden (Kopfzeile mit Zeilenumbruch oder Zeichen außerhalb von Latin-1, Host nicht als IDNA kodierbar, unlesbare Proxy-Adresse) sind Einstellungs- oder Programmfehler: laut, nicht gezählt, keine Pausen; `RATSATLAS_KONTAKT` wird ohne Leerraum am Rand übernommen. Als Nacht mit möglicher Sperre zählen außerdem HTTP 401/403/429, „aufgegeben“ nach 429/5xx oder unlesbaren Antworten, Weiterleitungen und „unlesbar“; nicht dagegen Ablehnungen durch einen Proxy der Ausführungsumgebung und ungültige Adressen (sie haben die Stadt nie erreicht) sowie ein Vollabruf mit weniger als 90 % der bisherigen Objekte (Abbruch der Art `leer`). Nach jedem Abbruch außer dem Ende des Zeitfensters (auch nach einer Ablehnung durch den Proxy, einer ungültigen Adresse oder einem Programmfehler) folgt in derselben Nacht (12 h) kein weiterer Lauf (`letzter_abbruch`); nach drei Nächten mit möglicher Sperre ohne vollständigen Lauf dazwischen sieben Tage Pause. Abbrüche wegen ungültiger Folgeadressen oder Schleifen in `links.next` (ohne Fortsetzung, also jede Nacht ein Vollabruf von vorn) und wegen eines nicht angewandten Zeitfilters (Art `filter`, siehe unten) zählt `listenfehler` (Nächte, nicht Läufe): Hinweis in `STAND.json` (`abruf_hinweis`), Warnung im Workflow-Log, nach drei Nächten sieben Tage Pause. Vor der ersten Anfrage wird der Zustand geprüft: Eine unlesbare Datei oder ein unlesbarer Zeitpunkt einer Liste bricht ohne Anfrage mit Fehler ab, bei jedem Lauf, bis die Datei geprüft ist (Abhilfe in GitHub Actions: den jüngsten Zwischenspeicher `raw-…` unter Actions → Caches löschen, dann nimmt der nächste Lauf den vorigen Stand; kein automatisches Neuanlegen); ein unlesbarer, zonenloser oder künftiger Zeitpunkt des letzten Sperrverdachts, Listenfehlers oder Abbruchs gilt als „jetzt“, eine unlesbare Zahl der Nächte als drei, ein unlesbares `nicht_vor` als jetzt + 7 Tage, eines mehr als 30 Tage voraus als jetzt + 30 Tage (alles neu geschrieben und gemeldet); eine unlesbare Fortsetzung wird verworfen. Programm- und Einstellungsfehler (auch ein `RuntimeError` ohne Art, etwa `RecursionError`) zählen nicht als Sperrverdacht, sondern brechen mit Traceback ab (Abrufschritt rot, die alte Seite bleibt online) und stehen in `STAND.json`. Jeder andere Abbruch außer dem Ende des Zeitfensters und der Obergrenze je Nacht (der Abrufschritt bleibt grün) erscheint als Warnung im Workflow (`::warning::`), bei möglicher Sperre mit der Zahl der Nächte; ebenso ein übersprungener Lauf wegen der 12-Stunden-Regel, eines Retry-After oder der Pause nach drei Nächten, nicht aber ein Lauf außerhalb des Zeitfensters (Push tagsüber). Ein vollständiger Lauf entfernt `abruf_fehler`, `abruf_hinweis` und `abruf_uebersprungen`; die Seite meldet einen fehlgeschlagenen Abruf nur, wenn er nach dem letzten vollständigen liegt. Endet das Zeitfenster während eines Vollabrufs über mehrere Nächte oder erreicht er die Obergrenze je Nacht (Art `obergrenze`), ist das kein Fehler: neutraler Hinweis in `abruf_hinweis` („Obergrenze je Nacht erreicht, Fortsetzung in der nächsten Nacht“), kein Listenfehler, kein Sperrverdacht; nach der Obergrenze gilt die 12-Stunden-Regel (höchstens einmal je Nacht bis zur Grenze). Wie es weitergeht, leitet der Hinweis aus dem Zustand ab, nicht aus der abbrechenden Liste: Steht eine Fortsetzung einer Liste aus, „Fortsetzung in der nächsten Nacht“, sonst beginnt der Abruf in der nächsten Nacht erneut (ein inkrementeller Lauf speichert keine Fortsetzung). Ein inkrementeller Lauf, der länger als ein Zeitfenster braucht, beginnt so jede Nacht neu (bestehendes Verhalten, nicht umgebaut). Erreicht ein inkrementeller Lauf die Grenze je Lauf (Listenfehler `liste`), verweist der Hinweis auf `RATSATLAS_VOLLABRUF=ja` (Vollabruf, über mehrere Nächte fortgesetzt). `pages.yml` sichert den Zustand gleich nach dem Abrufschritt, auch wenn ein späterer Schritt scheitert. User-Agent `ratsatlas-koeln/0.1 (+https://github.com/daimpad/ratsatlas-koeln; <RATSATLAS_KONTAKT>)`. Listen nur über `links.next`. Parameter gehen URL-kodiert hinaus (`quote(wert, safe="")`): Köln übergeht Zeitwerte unkodiert (gleiche Seite wie ohne Filter) und wendet sie kodiert an (Stufe 2, 08.11.2026, `explore/BERICHT_phase1.md` Abschnitt 6; ersetzt für Köln die Annahme „Parameter ohne URL-Kodierung“ vom 05.11.2026, die aus anderen SessionNet-Installationen mit HTTP 404 bei kodierten Werten stammte). `links.next` gibt den Filterwert unkodiert zurück (`…?page=2&modified_since=2026-11-05T11:29:44+00:00`) und wird vor dem Folgen normalisiert: Schema, Host und Pfad bleiben, der Query-Teil wird je Parameter als `k=quote(unquote(v), safe="")` neu aufgebaut (Reihenfolge, `page` und `limit` unverändert, idempotent; `unquote`, nicht `unquote_plus`, weil Köln „+“ als wörtliches Plus liefert); zeigt `links.next` auf einen anderen Host oder Port als die Liste (ein ausdrücklicher Standardport wie `https://…:443` gilt wie keiner), wird nichts gesendet (Art `adresse`). Der Schleifenschutz und die Fortsetzung arbeiten mit der normalisierten Adresse. Offen: Ob Köln auf Seite 2 mit kodiertem Filter weiter filtert, ist ungemessen; die Abrufstatistik prüft je Lauf über alle Seiten (`filter_wirksam`, auch bei einem Abbruch aus den bis dahin gelesenen Seiten), und ein inkrementeller Lauf prüft jede Seite: Enthält sie Objekte mit lesbarem `modified` vor `modified_since` (die Überlappung von einem Tag ist dort schon abgezogen; Löschungen mit `deleted: true` ausgenommen, sie können ein altes `modified` tragen), wendet der Server den Filter nicht an. Bei den Vorlagen bricht der Lauf dann nach dieser Seite ab (Art `filter`, „Zeitfilter auf Seite N nicht angewandt“ in Abrufstatistik und `STAND.json`; zählt wie ein Listenfehler, nach drei Nächten sieben Tage Pause), statt bis zum Fensterende die ganze Liste zu lesen; Seite 1 der Vorlagen löst das in Kölner Form nicht aus (Stufe 2: kodiert keine Vorlage unter der Grenze). Bei den Sitzungen liest der Lauf die Liste dann in derselben Nacht vollständig (Entscheidung 10.11.2026, umgesetzt in Runde 20; `sessionnet._abruf_liste` mit `voll_ohne_filter`): neu ab Seite 1 ohne `modified_since`, also eine Anfrage mehr, statt `links.next` der gefilterten Seite weiter zu folgen. Begründung: Ob Köln den Filter auf Folgeseiten ebenso übergeht und ob die Seitengrenzen mit und ohne Filter gleich sind, ist ungemessen; ein „Vollabruf“, auf dessen Folgeseiten der Filter doch wirkte, ersetzte den Stand unbemerkt durch einen Teil (unter 90 % fiele es auf, darüber nicht). Der Neustart sendet dieselben Anfragen wie ein Vollabruf der Sitzungen (`RATSATLAS_VOLLABRUF=meetings`) und gilt wie einer: 90-%-Regel gegenüber dem Stand (Art `leer`: Abbruch des Laufs, Stand bleibt, jede Nacht erneut; Abhilfe `RATSATLAS_KUERZER_ANNEHMEN=meetings`; seit der Prüfung r20 nennt die Meldung in `STAND.json` den Anlass „vollständiges Lesen nach nicht angewandtem Zeitfilter“ und diese Abhilfe, die Abrufstatistik Seiten und Objekte), der Stand wird ersetzt, nicht zusammengeführt (eine in der Quelle entfernte Sitzung fehlt danach); beenden ihn das Zeitfenster oder die Obergrenze je Lauf, folgt die Fortsetzung in der nächsten Nacht. Die Seiten mit Zeitfilter zählen zur Grenze je Lauf (`liste(…, im_lauf=…)`), nicht zu den Seiten des Vollabrufs (Gesamtgrenze, `meetings_fortsetzung.seiten`); ist die Grenze schon mit ihnen erreicht (Befund auf der letzten erlaubten Seite), folgt keine Anfrage mehr (Art `obergrenze`, ohne Fortsetzung, die nächste Nacht beginnt wieder mit Zeitfilter; Prüfung r20: vorher eine Seite ohne Filter zu viel, weil `liste()` vor der ersten Seite die Seitengröße nicht kennt). Jede Nacht, nicht jeder Lauf (Prüfung r20): Ein weiterer Lauf in derselben Nacht (Push auf `main` im Zeitfenster, den die concurrency-Gruppe „pages“ hinter den Nachtlauf reiht, Knopfdruck oder ein neu gestarteter Job; nach einem vollständigen Lauf greift die 12-Stunden-Regel nicht) liest die Sitzungen nicht noch einmal vollständig, wenn sie in dieser Nacht schon gelesen sind (Zustand `meetings`, Beginn des letzten erfolgreichen Lesens, oder `meetings` in `STAND.json`, sein Ende, auch das einer Fortsetzung, die erst in dieser Nacht fertig wurde (Prüfung r20n; vorher galten die Sitzungen nach einer Fortsetzung als in der Vornacht gelesen und ein weiterer Lauf las sie noch einmal vollständig); der spätere dieser Zeitpunkte, weniger als 12 Stunden zurück, ein künftiger zählt nicht; `sessionnet._in_dieser_nacht_gelesen`, nicht für lokale Testserver wie die 12-Stunden-Regel): Mit dem Vermerk `meetings_ohne_zeitfilter` aus dem früheren Lauf ohne Anfrage (wie bis Runde 19), sonst nach dem Befund auf den k Seiten mit Zeitfilter (etwa nach dem ersten Vollabruf oder `RATSATLAS_VOLLABRUF=meetings` in derselben Nacht); letzter gültiger Stand, `meetings.json` und ihr Zeitpunkt unverändert, keine Warnung in `STAND.json`, Zeile mit `ergebnis` „übersprungen: … in dieser Nacht schon gelesen (zuletzt …) …“ in der Abrufstatistik (`modus` „übersprungen“ bzw. „inkrementell“), Meldung im Log (`sessionnet._schon_gelesen`). Ohne diese Regel kostete jeder weitere Lauf der Nacht noch einmal k + ⌈M / 100⌉ Anfragen. Kein Listenfehler, keine Pause, keine Warnung in `abruf_warnungen` (die Sitzungen sind aktualisiert); Warnung „Zeitfilter bei Sitzungen nicht angewandt, Sitzungen vollständig gelesen (N Seiten ohne modified_since nach k mit Zeitfilter); Befund: …“ im Log und als `ok; …` in der Abrufstatistik (`modus` „voll, Zeitfilter nicht angewandt“, `filter_wirksam` „nein (… ältere)“ aus den Seiten mit Zeitfilter, `anfragen` mit ihnen). Jede Nacht beginnt die Liste wieder mit Zeitfilter: Wendet der Server ihn wieder an, bleibt der Lauf ohne Zutun inkrementell. Ob Köln `modified_since` bei den Sitzungen anwendet, ist ungemessen; die Abrufstatistik zeigt es nach der ersten inkrementellen Nacht. Mehranfragen, solange der Server den Filter übergeht: je Nacht ⌈M / 100⌉ Seiten ohne Filter zusätzlich zu den k Seiten mit Filter bis zum Befund (meist k = 1; M Sitzungen insgesamt, ungemessen, nach dem ersten Vollabruf in der Spalte `objekte` der Zeile `meetings`); bei 5 000 bis 20 000 Sitzungen (Schätzung wie unten bei den Variablen, ungemessen) 51 bis 201 Anfragen je Nacht, mit 2 s Abstand und 3 bis 6 s Antwortzeit rund 4 bis 27 Minuten des Zeitfensters (Schätzung: Stufe 2 maß für die erste Sitzungsseite mit 25 Sitzungen 19,6 KB in 1,46 s, für 100 Vorlagen 5,07 s; 100 Sitzungen je Seite ungemessen); ein weiterer Lauf derselben Nacht 0 bzw. k Anfragen (siehe oben). Bis Runde 19 las der Lauf nach dem Befund keine Sitzungen mehr (Folgenächte ohne Anfrage), die Sitzungen blieben also bis zu einem Vollabruf veraltet. Die Organisationen ruft der Abruf immer ohne Zeitfilter und vollständig ab, auch im inkrementellen Lauf, ohne Filterprüfung: eine kleine Liste (den Umfang misst Stufe 3), und Münster lehnt `modified_since` bei `organization` mit HTTP 401 ab (`explore/ergebnisse/sessionnet_befunde.tsv`; mandari ruft sie dann ohne Filter ab). Weil sie vor den Vorlagen kommen, beendet ein Vollabruf der Organisationen unter 90 % des Stands (Art `leer`) nur diese Liste (letzter gültiger Stand, Warnung in `abruf_warnungen`), statt jede Nacht die Vorlagen zu blockieren. Offen: Eine Antwort HTTP 401 auf einen Zeitfilter wie in Münster wertet die Pipeline heute als Nacht mit möglicher Sperre (Art `http`); bei den Sitzungen hieße das jede Nacht einen Abbruch auf ihrer ersten Seite (die Vorlagen sind dann schon gelesen, die Beratungen nicht abgeleitet) und nach drei Nächten sieben Tage Pause, auch für die Vorlagen (nicht umgebaut; vor der Freigabe messen). Ebenfalls ungemessen: `limit=100` für `meetings` und `organizations` (Stufe 2 nur mit 25 je Seite, Sitzungen Seite 1: 19,6 KB in 1,46 s); Messung in einer späteren Stufe. Seitengröße `limit=100` (`RATSATLAS_LIMIT`, Stufe 2: 100 Vorlagen in 5,07 s, `next` mit `limit=100`) an der ersten Listenadresse; trägt `links.next` ihn nicht, wird er angehängt. Alle seitenbezogenen Grenzen gelten in Objekten und werden mit der tatsächlichen Seitengröße des Laufs (größte gelesene Seite) in Seiten umgerechnet: höchstens `RATSATLAS_MAX_OBJEKTE` (100 000, bei 100 je Seite 1000 Seiten) je Liste und Lauf als Höflichkeitsgrenze je Nacht (höchstens rund 1000 Anfragen je Liste und Nacht): Ein Vollabruf endet dort wie am Ende des Zeitfensters (Art `obergrenze`) und wird in der nächsten Nacht fortgesetzt (die Grenze zählt dort neu), sofern der Lauf über die wiederholte Seite einer Fortsetzung hinaus neue Objekte gelesen hat (sonst Abbruch `liste`: die Fortsetzung käme nie voran); ein inkrementeller Lauf bricht dort als Listenfehler ab (Art `liste`). Werte von `RATSATLAS_MAX_OBJEKTE` unter (⌈1000 / g⌉ + 2) · g mit g = `RATSATLAS_LIMIT` (zwei Seiten plus die größte Seitenverschiebung von 1000 Objekten, aufgerundet auf Seiten; bei 100 je Seite 1200, bei 150 1350; leeres `RATSATLAS_LIMIT` gerechnet wie 100; also auch 0 und negative) lehnt der Abruf vor der ersten Anfrage als Einstellungsfehler ab (laut, kein Sperrverdacht), ebenso ein `RATSATLAS_LIMIT`, das keine positive ganze Zahl ist. Annahme: Der Server liefert g Objekte je Seite wie verlangt. Über alle Fortsetzungen eines Vollabrufs höchstens 600 000 Objekte (`ABRUF_MAX_OBJEKTE_GESAMT`, Schleifenschutz; ein Vollabruf mit bis zu 500 000 Objekten je Liste wird so sicher fertig; geprüft vor der Grenze je Lauf und ab der zweiten Anfrage eines Laufs, sonst Abbruch wie bei einer Schleife). Das ist eine Abwägung: Eine Liste, die endlos neue Kennungen erzeugt, erkennt diese Grenze erst nach rund sechs Nächten (bis zu 1000 Seiten zu 100 je Nacht, also bis zu rund 6000 Anfragen); eine engere Grenze gefährdete den Vollabruf großer Listen (bis 500 000 Objekte). Abbruch auch bei Seiten ohne neue Kennungen. Kapazität je Nacht (Start 23:10 Uhr, im Sommer 0:10 Uhr; Ende 1 Uhr; rund 108 bzw. 48 Minuten nach der Einrichtung des Laufs): mit 100 je Seite rund 7 s je Seite (5,1 s Antwort plus 2 s Abstand), also rund 900 Seiten oder 90 000 Objekte (im Sommer rund 400 Seiten, 40 000 Objekte); bei schnellen Antworten (3 s) wären es rund 1300 Seiten, die Obergrenze je Nacht beendet den Lauf dann nach 1000 Seiten; mit 25 je Seite (2,3–2,8 s Antwort) rund 1400 Seiten oder 35 000 Objekte. Bei rund 135 000 Vorlagen (höchste Kennung in Stufe 1) braucht ein Vollabruf der Vorlagen so zwei Winternächte statt vier, dazu Organisationen und Sitzungen (Umfang unbekannt). `pipeline/abruf.py` kennt keine Grenze für langsame Antworten; die Zeitüberschreitung je Anfrage bleibt 90 s. Köln liefert die Vorlagen neueste zuerst und ohne Gesamtzahlen (`pagination` nur `elementsPerPage` und `currentPage`, Stufe 1): Neue Vorlagen zwischen zwei Nächten verschieben die Seiten nach hinten; in einer Fortsetzung gelten Seiten ohne neue Kennungen bis zu einer Verschiebung von 100 Vorlagen je angefangenem Tag seit dem Speichern der Fortsetzung (`gespeichert`, höchstens 1000; `verschiebung_erlaubt`), aufgerundet auf Seiten (bei 100 je Seite eine je Tag, bei 25 vier; genauer bis zu 99 neue Vorlagen je Tag, weil die wiederholte Seite mitzählt) als Seitenverschiebung, nicht als Schleife; bricht eine Fortsetzung ab, bevor sie die verschobene Zone verlassen hat (noch keine ungelesene Vorlage, deren `created` nicht jünger ist als das der g-ältesten gelesenen, g = tatsächliche Seitengröße, also eine Seite; gleich alt genügt, bis zu g − 1 Platzhalterdaten unter den gelesenen stören nicht), bleibt `gespeichert` (die Verschiebung seit dann besteht weiter). Das setzt voraus, dass Köln die Liste streng nach `created` absteigend sortiert; belegt ist das für die ersten 100 Vorlagen (Stufe 2), über mehrere Seiten noch nicht. Trifft es nicht zu, gilt die Zone zu früh als verlassen (in der Folgenacht womöglich ein Listenfehler) oder nie (erlaubte Verschiebung bis 1000 Vorlagen, ein schwächerer Schutz gegen Schleifen); eine Seite, deren Kennungen alle schon in diesem Lauf kamen, und eine wiederholte Adresse bleiben eine Schleife. Die Fortsetzung beginnt eine Seite vor der Abbruchstelle (eine Anfrage mehr, zählt als Verschiebung): So gehen bis zu einer Seite (bei 100 je Seite 100) zwischen den Nächten gelöschter Vorlagen nicht zulasten der folgenden; bei mehr Löschungen können Vorlagen bis zum nächsten Vollabruf fehlen. Zwischen den Nächten gelöschte, schon gelesene Vorlagen bleiben bis zum nächsten Vollabruf bzw. bis zu ihrem Eintrag mit `deleted` aus `modified_since` im Stand. Doppelungen werden über die Kennung zusammengeführt, die neuen Vorlagen am Listenanfang holt der nächste inkrementelle Lauf; ab dem zweiten vollständigen Lauf `modified_since` mit einem Tag Überlappung (`RATSATLAS_VOLLABRUF=ja` erzwingt einen Vollabruf). Ein Vollabruf ersetzt den Stand nur, wenn er mindestens 90 % der bisherigen Objekte enthält. `pipeline/net.py` (aus Bonn: Wiederholungen, mehrere Verbindungen, kein Zeitfenster) verweigert Anfragen an Adressen der Stadt (stadt-koeln.de, offenedaten-koeln.de, Host der OParl-API), auch als Ziel einer Weiterleitung (ein unlesbares Ziel gilt vorsichtshalber als Adresse der Stadt); solche Abrufe, etwa `fetch-besetzung`, gehören auf `pipeline/abruf.py` umgestellt. Module, die direkt über urllib abrufen (`geodaten.py`, `ebenen.py`, `kontext.py` u. a.), erfasst dieser Schutz nicht.

Eine gespeicherte Fortsetzung gilt nur dann als veraltet und wird verworfen, wenn schon ihre erste Seite HTTP 404 oder 410 liefert (`sessionnet.VERALTET_HTTP`); bei 401, 403 und anderen Codes bleiben Fortsetzung und Teildatei für die nächste Nacht, 401 und 403 zählen wie bisher als Nacht mit möglicher Sperre. Antworten werden mit `json.loads(…, strict=False)` gelesen: rohe Steuerzeichen in Zeichenketten (etwa \x0b in einem Titel) machen eine Seite nicht unlesbar, ungültiges UTF-8 und kein JSON bleiben unlesbar (Wiederholungen, dann `aufgegeben`).

Nebenlisten (Sitzungen, Organisationen; Runde 17; seit Runde 20 schreibt nur die Liste der Organisationen eine Warnung, eine Warnung der Sitzungen aus älterem Code bleibt lesbar und entfällt mit der nächsten Aktualisierung der Sitzungen): Ihre Warnungen stehen in `STAND.json` unter `abruf_warnungen` je Liste (`zeit`, `meldung` mit Abhilfe), nicht in `abruf_hinweis`; sie werden beim Auftreten vermerkt, ein späterer Abbruch einer anderen Liste und ein vollständiger Lauf lassen sie stehen, entfernt wird die Warnung einer Liste erst, wenn diese Liste wieder regulär aktualisiert wurde. `export` übernimmt gültige Warnungen (nicht vor der letzten regulären Aktualisierung der Liste) in `index.json` (`meta.abruf_warnungen`, mit dem Stand der Liste); die Seite zeigt sie im Datenstand in einfacher Sprache („Sitzungstermine wurden beim letzten Abruf nicht aktualisiert; gezeigt wird der Stand vom …“, ebenso für die Liste der Gremien). Alle Daten im Datenstand (Abrufdatum der Quellen wie „Ratsinformationssystem: …“, „erzeugt …“, „Stand vom …“ und „Der letzte Abruf am …“) folgen einer Regel: Datum des vollen Zeitstempels in Europe/Berlin (23:30 UTC ist dort schon der nächste Tag; ein Zeitstempel ohne Zone gilt als UTC, damit das Datum nicht von der Zone des Rechners abhängt); ist nur der Anfang lesbar, die ersten zehn Zeichen, sonst „unbekannt“. Nach derselben Regel entsteht der Datenstand für die Markierung in der Zeitleiste und die Jahresgrenze der Vorgangs-Feeds (`dataStand`, Berliner Kalendertag), nur aus einem lesbaren Wert: Abruf des Ratsinformationssystems, sonst `generated_at`, sonst heute; die Pipeline bildet die Jahresgrenze der Feeds je Vorlage ebenso (`export.feed_grenze` über `export.berliner_tag`: 1. Januar des Vorjahres des Berliner Kalendertags von `retrieved_at`, unlesbar heute in Berlin), sodass ein Abruf am 31.12. um 23:30 UTC in Pipeline und Seite zum Jahr 2027 zählt (Runde 17e); ein unlesbarer Wert (Text, Zahl, Objekt) bringt die Seite nicht zum Absturz, und `#stand` wird vor der Zeitleiste gesetzt. Wendet der Server `modified_since` bei den Sitzungen nicht an, liest der Lauf sie vollständig (siehe Abrufpolitik oben) und vermerkt den Befund im Zustand (`meetings_ohne_zeitfilter` mit `zeit` und `meldung`, dieselbe Form wie bis Runde 19); der Vermerk dient nur der Auskunft und wird nicht ausgewertet. Er entfällt, sobald ein Lauf die Sitzungen ohne Befund liest (inkrementell mit wirksamem Filter oder vollständig, auch als Fortsetzung oder mit `RATSATLAS_VOLLABRUF=meetings`). Ein Vermerk aus älterem Code (bis Runde 19: Folgenächte ohne Anfrage), auch in unlesbarer Form, ändert nichts mehr; umgekehrt läse der Code bis Runde 19 den neuen Vermerk wie seinen eigenen und übersprünge die Sitzungen (geprüft mit beiden Ständen gegen den lokalen Testserver). Ist ein Vollabruf einer Liste kürzer als 90 % des Stands und stimmt das (etwa weniger Gremien nach einer Wahlperiode), nimmt ein Lauf mit `RATSATLAS_KUERZER_ANNEHMEN=organizations` (Komma-Liste aus `organizations`, `papers`, `meetings`) den kürzeren Stand an (einen Vollabruf ohne Objekte nie, auch keinen nur mit gelöschten Objekten; Abbruch `leer` wie ohne die Einstellung), mit Warnung im Log und Vermerk in der Abrufstatistik (`ok; kürzerer Stand angenommen …`). Die Einstellung ist ausdrücklich und nur für diesen einen Lauf zu setzen, nie als Vorgabe; danach gilt die 90-%-Regel gegenüber dem neuen Stand. Die 90-%-Prüfung der abgeleiteten Beratungen entfällt nur, wenn für `papers` oder `meetings` tatsächlich ein kürzerer Stand angenommen wurde, nicht schon, weil die Liste in der Einstellung steht (auch nicht nach einem angenommenen kürzeren Stand der Organisationen); bricht der Lauf danach vor den Beratungen ab (etwa am Ende des Zeitfensters), hält der Zustand das fest (`beratungen_kuerzer_erlaubt` mit Zeit und Listen), sodass die nächste Nacht, die die Beratungen erreicht, sie auch ohne die Einstellung ableitet; entfernt wird der Vermerk erst nach dem Schreiben von `beratungen.jsonl`, und einen leeren Beratungsstand (0 bei bisher über 0) nimmt der Abruf nie an. Hauskoordinate nur bei erkennbarer Vorlagenart (Entscheidung 10.11.2026): `geocode.VORLAGENART_PUNKT` erkennt Verwaltungsvorlagen und politische Anträge und Anfragen (Kölner Arten aus Stufe 1 und 2, Bonner bzw. übliche SessionNet-Arten, Groß- und Kleinschreibung egal; Eingaben und Einwohneranfragen gehen vor); bei leerer, nicht erkennbarer oder nicht als Text gelieferter Vorlagenart bleibt es wie bei Eingaben beim Straßenabschnitt (`strasse+hausnummer`), und wie bei Eingaben gilt das für alle verbundenen Vorlagen (über- und untergeordnet und `relatedPaper`; vorsichtige Auslegung), in `build` und `check.erlaubnis` gleich. Arten mit „Bürger“ (außer „Bürgermeister“), „Einwohner“, „Anwohner“, „privat“, „Bauantrag“ oder „Bauvoranfrage“ gelten nie als erkannt. Abgeglichen wird ein Vergleichstext (`geocode._vergleichstexte`, auch für Eingaben und Gremien): Unicode NFKC, ohne weiche Trennzeichen und Zeichen ohne Breite, kleingeschrieben, Leerraum am Rand entfernt und im Text zu einem Leerzeichen zusammengefasst (Prüfung r20n), „Paragraf 24“ wie „§ 24“, dazu dieselbe Fassung mit „ae/oe/ue“ als „ä/ö/ü“ („Buergerantrag“); ein Ausschluss gilt bei einem Treffer in einer der beiden Fassungen, eine Erkennung nur bei Treffern in beiden. Gibt es eine Drucksache mehrfach, verliert jede Vorlage mit der Drucksache einer gesperrten Vorlage ebenfalls die Hauskoordinate (`geocode.sperrmenge`), weil `vorlagen.geojson` und die Gebietsdateien Vorlagen unter ihrer Drucksache führen und `check.erlaubnis` dort jede Vorlage dieser Drucksache prüft; der Aufbau urteilt so wie die Prüfung, statt die Veröffentlichung mit einem Befund anzuhalten (seit Runde 19b als Fixpunkt, siehe unten). Die nicht erkannten und die erkannten Arten stehen mit Anzahl im Log von `build` und in der Ausgabe von `check` („Vorlagenart nicht erkennbar …“, „Vorlagenart erkannt, Hauskoordinate möglich …“, nur die Art), damit das Muster nach dem Vollabruf in beide Richtungen geprüft und ergänzt werden kann; die Zeile „Ohne Erlaubnis für Hauskoordinaten“ zählt Gründe, verbundene Vorlagen und Vorlagen mit derselben Drucksache. Die Hausnummer im Titel blendet `maske.py` weiter nur bei Eingaben, Einwohneranfragen, Vorlagenarten aus der Einwohnerschaft oder von Privatpersonen (`geocode.art_von_personen`, dieselbe Regel wie der Ausschluss in `VORLAGENART_PUNKT`; Prüfung r20n), Bauordnung und Naturschutz und den mit ihnen verbundenen Vorlagen aus, nicht wegen einer sonst nicht erkennbaren Vorlagenart und nicht wegen einer Beratung im Ausschuss für Anregungen und Beschwerden (Grund „gremium“, offen; `maske.kette`, siehe unten).

Menge ohne Hauskoordinate als Fixpunkt (Runde 19b, Prüfung r19): `geocode.sperrmenge` ist die eine Funktion für `build` (`build._ohne_hauskoordinate`) und `check.erlaubnis`. Startmenge sind die Vorlagen mit Grund aus `geocode.punkt_ausschluss` und die ausgelassenen Vorlagen; danach kommen abwechselnd die verbundenen Vorlagen (über- und untergeordnet und `relatedPaper`, in beiden Richtungen) und die Vorlagen mit derselben Drucksache hinzu, bis nichts mehr hinzukommt. Gerechnet wird das als eine Breitensuche in Schichten in linearer Zeit (Nachbarn und Vorlagen je Drucksache einmal aufgestellt, jede Drucksache einmal; Prüfung r19b: vorher je Wechsel zwischen Beziehung und Drucksache ein Durchlauf über alle Vorlagen, laut Messung der Prüfung brauchte eine erfundene Kette aus 1600 Vorlagen neben 135 000 weiteren 48 s je Aufruf); Menge und Wege sind dieselben wie beim früheren Ablauf in Runden (Test mit zufälligen Beständen). Dazu:
- `relatedPaper` steht in der Tabelle `paper_related` (auch bei ausgelassenen Vorlagen) und zählt für den Datenschutz wie eine Beziehung: für die Hauskoordinaten und seit Runde 20 auch für Titelmaske und Volltextkette (nächster Punkt); `paper_relation` und die Folgevorlagen im Export bleiben ohne `relatedPaper`. Vorher bekamen diese Arten über `VORLAGENART_PUNKT` keine Hauskoordinate (Grund „vorlagenart“), zeigten die Hausnummer aber im Titel, ohne Befund in `check`. Vorher verglich die Maske die gelieferte Schreibung: Eine Eingabe als „Buergerantrag“, mit weichem Trennzeichen oder „Paragraf 24“ verlor die Hauskoordinate, zeigte die Hausnummer aber im eigenen Titel und in den Titeln der verbundenen Vorlagen, ohne Befund in `check`), für die Titelmaske auch Bauordnung und Naturschutz federführend (`maske.privat`), und die ausgelassenen Vorlagen; daraus rechnet `geocode.sperrmenge` mit denselben Beziehungen wie für die Hauskoordinaten den Fixpunkt über verbundene Vorlagen (über- und untergeordnet und `relatedPaper`, in beiden Richtungen, wie dort auch über Kennungen, die im Bestand fehlen) und dieselbe Drucksache. Die Beziehungen liefern `geocode.beziehungen` (Rohdaten: `build` für `paper_relation`, `paper_related`, Fixpunkt und Volltextkette) und `geocode.beziehungen_db` (Datenbank: `maske.aus_db`, `check.erlaubnis`). Vorher folgten Maske und Volltextkette mit eigener Breitensuche (`chat.einwohner`, entfernt) nur über- und untergeordneten Vorlagen: Eine Stellungnahme, die nur über `relatedPaper` mit einer Eingabe verbunden war, bekam keine Hauskoordinate, zeigte die Hausnummer aber im Titel. Weil jede Ausgangsvorlage der Maske auch ohne Erlaubnis ist (Grund „Titel ohne Hausnummer“, nächster Punkt), liegt die Maske in der Menge ohne Hauskoordinate; `check` meldet eine Drucksache der Maske mit Erlaubnis als Befund („Titel ohne Hausnummer (maske.py), aber Erlaubnis für Hauskoordinaten …“) und seit der Prüfung r20 auch die Gegenrichtung: jede Vorlage mit Grund „eingabe“ (`geocode.punkt_ausschluss`), deren Drucksache nicht in der Maske liegt („Eingabe oder Einwohneranfrage ohne Hauskoordinate …, aber nicht in der Titelmaske“), seit der Prüfung r20n ebenso jede Vorlage, deren Vorlagenart `geocode.art_von_personen` erfüllt. Offen (Entscheidung des Auftraggebers, bestand schon vorher): Vorlagen, die nur wegen einer Beratung im Ausschuss für Anregungen und Beschwerden bzw. für Bürgerbeteiligung keine Hauskoordinate bekommen (Grund „gremium“), sind kein Ausgangspunkt der Titelmaske; ihr Titel zeigt die Hausnummer weiter, `check` meldet das nicht. Möglich wäre, die Gremienregel aus `punkt_ausschluss` als eigene Funktion in `maske.kette` aufzunehmen (`maske.aus_db` liest die Gremien wie `check.erlaubnis`). Das Log von `build` nennt nur Zahlen: „Titelmaske (…): n Vorlagen; nur über relatedPaper: k Vorlagen, davon j mit gekürztem Titel“. Gemessen an einem erfundenen Bestand mit 139 000 Vorlagen etwa 1 s je Aufruf, linear.
- Schreibweisen der Hausnummer (Prüfung r20n): `maske.Maske` gleicht eine angeglichene Fassung des Titels ab (`maske._angleichen`: je Zeichen NFKC, also Vollbreite, „№“ als „No“ und geschütztes Leerzeichen als Leerzeichen; ohne weiche Trennzeichen und Zeichen ohne Breite; jeder Leerraum, auch Zeilenumbruch oder doppelt, als ein Leerzeichen) und ersetzt über die Stellen im gelieferten Titel, der sonst unverändert bleibt. Zwischen Straße und Nummer stehen bis zu drei Zeichen außer Buchstaben und Ziffern oder keines, wenn die Straße nicht auf eine Ziffer endet („Str.12“, „Straße12“, „Straße, 12“, „Straße (Nr. 12)“, „Straße #12“; nicht „L 84“ vor „5“), danach wahlweise „Nr.“, „No.“, „Nummer“ oder „Haus“ (fallen mit der Nummer weg); „Str“ auch ohne Punkt; Straßennamen ohne Endung auch mit „ss“ statt „ß“ und umgekehrt („Am Schlossgarten“). Vorher ließen diese Schreibweisen die Hausnummer stehen, und `check` prüfte mit demselben Muster. Seither prüft `check` (`Maske.offen`) zusätzlich mit einer unabhängig gebauten Probe (`maske._Probe`: ganzer Titel NFKC und casefold, Ziffernfolge mit bis zu vier Stellen hinter einem Straßennamen oder einem Wort mit Straßen-Endung, bis zu vier Trennzeichen); nicht hinter einem bloßen „Nr.“ oder „Haus“ (Bebauungsplan-, Drucksachen- und Gebäudenummern; ein Befund hielte die Veröffentlichung an). Die Geokodierung liest diese Schreibweisen weiter nicht als Hausnummer (nur Straße). Kosten: `offen` braucht mit der Probe etwa 4,6 statt 2,8 ms je gekürztem Titel mit Ziffer (gemessen mit dem Kölner Straßenverzeichnis).
- Offen (Prüfung r20n, Entscheidung nach dem Vollabruf mit den Zahlen aus dem Log von `build`): Teilwörter in `geocode.EINGABE` machen gewöhnliche Vorlagen zur Eingabe (ohne Hauskoordinate, Hausnummer im Titel ausgeblendet): „Vorkaufsrecht nach § 24 BauGB“ (auch „Paragraf 24 BauGB“), „Online-Eingabeportal“, „Beschwerdemanagement“, „Verfassungsbeschwerde“, „Anregungen aus der Öffentlichkeit(sbeteiligung)“; seit der Prüfung r20n auch „Bürgerfrage(stunde)“ und „Bürger fragen …“ im Titel. Über `chat.EINWOHNER_TITEL` gilt das für jedes „Einwohner…“ im Titel („Einwohnerzahl“, „Einwohnerbefragung“; Grund „maske“), obwohl „Einwohnerbefragung“ nach `EINGABE` keine Eingabe ist, und über `geocode.art_von_personen` für jede Vorlagenart mit „Bürger“ außer „Bürgermeister“ (etwa „Mitteilung Bürgerbeteiligung“). Das kostet Genauigkeit, nicht Datenschutz. Möglich wären `§\s*24(?!\d)(?!\s*(?:abs\.?\s*\d+\s*)?(?:baugb|bnatschg|kag|stvo))` und Ausnahmen wie „eingabe(?!portal|maske|feld)“ und „beschwerde(?:management|stelle)“.
- Grund „Titel ohne Hausnummer“ (`maske.titel_ohne_hausnummer`, mit denselben Angaben wie `maske.aus_db`: Art und Titel aus der Einwohnerschaft, darunter „Einwohner“ im Titel, oder Bauordnungsamt bzw. Untere Naturschutzbehörde federführend nach dem Namen der Organisation aus `underDirectionOf`): Neben einem Titel, dessen Hausnummer ausgeblendet ist, steht keine Anschrift als Ortsname mit Hauskoordinate. Damit liegt jede Vorlage, deren Titel `maske.py` kürzt, in der Menge ohne Hauskoordinate. Offen (Prüfung r19b, Entscheidung des Auftraggebers): Der Auftrag verlangte das nur für Bauordnung und Naturschutz (`maske.AMT_PRIVAT`); praktisch kommt das Wort „Einwohner“ im Titel einer erkannten Verwaltungsvorlage oder eines Antrags hinzu („Einwohnerversammlung …“, „… für 1200 Einwohnerinnen und Einwohner“), samt den damit verbundenen Vorlagen. Bis zur Entscheidung gilt die vorsichtigere Regel; das Log von `build` zeigt nach dem Vollabruf, was sie kostet („„Einwohner“ im Titel einer erkannten Vorlage …: n Vorlagen; ohne Hauskoordinate nur darüber: k Vorlagen“). Die andere Möglichkeit wäre, für diese Vorlagen statt des Punkts den Ortsnamen im Export zu kürzen.
- `build._inherited`: Eine gesperrte Vorlage erbt nie eine Hauskoordinate, sondern den Straßenabschnitt derselben Straße im Stadtteil der Hausnummer (wie die Rückfallstufe in Stufe B; Fundstelle „übergeordnete Vorlage … (Straßenabschnitt ohne Hausnummer)“), kennt das Straßenverzeichnis die Straße dort nicht, entfällt dieser Ortsbezug. Mit dem Fixpunkt ist die übergeordnete Vorlage einer gesperrten Vorlage selbst gesperrt; die Regel sichert das zusätzlich ab.
- Stufe A: Liefert die Ortsangabe einer gesperrten Vorlage einen Punkt (`geojson` Point), gilt er nur für seinen Stadtteil (Stadtteilfläche wie bei `subLocality`, Methode `oparl_sublocality`; Straße ohne Hausnummer bleibt als Name), außerhalb der Stadtteile ohne Koordinate. Das gilt auch für andere Vorlagen mit derselben Ortsangabe (vorsichtige Auslegung), auch wenn die gesperrte Vorlage beim Aufbau ausgelassen ist (Kennungen ihrer Ortsangaben in `skipped_location`; Prüfung r19b), und solche Ortsangaben liefern keinen Straßenpunkt für das Straßenverzeichnis.
- Stufe B und Volltext (Prüfung r19b): Eine Straße, die das Straßenverzeichnis nicht kennt, kennt der Gazetteer nur aus dem Punkt der Ortsangabe einer erlaubten Vorlage (Quelle `oparl-koeln`); dieser Punkt ist oft eine Anschrift. Für eine gesperrte Vorlage gilt eine solche Straße nur als Stadtteil des Punkts (`build._stadtteil_statt_stadtpunkt`: Ebene Stadtteil, Methode bleibt, Fundstelle „… (Straße nur aus einer Ortsangabe der Stadt bekannt: Stadtteil)“). Vorher stand eine Eingabe, die die Straße mit Hausnummer nennt, auf dem Punkt, den die Stadt für die Anschrift angibt.
- `check`: meldet genaue Punkte aus Ortsangaben der Stadt bei Vorlagen ohne Erlaubnis (Datenbank: jeder Ort der Quelle `oparl-koeln` mit Koordinate auf Ebene „strasse“, aus der eigenen Ortsangabe, vererbt oder aus Stufe B; `vorlagen.geojson` und Gebietsdateien: Methode `oparl_location` oder `location_source` bzw. `source` `oparl-koeln` mit Koordinate, in den Gebietsdateien auf Ebene „strasse“, in `vorlagen.geojson` ohne Ebene außer Stadtteil und vererbten Orten) und genaue Punkte auf einer Ortsangabe, die auch eine ausgelassene Vorlage nennt (`skipped_location`) und prüft unter Punkt 2 neben den Titeln auch die Ortsnamen (`place` in `vorlagen.geojson`, `locations[].name` in den Gebietsdateien) auf Hausnummern.

|---|---|---|
| `pages.yml` | täglich 22:10 UTC, bei Push auf `main`, auf Knopfdruck | Abruf (gesperrt bis zur Repository-Variable `RATSATLAS_STADT_INFORMIERT=ja`), Aufbereitung, Export, Datenpaket; Branch `deploy` (Hauptadresse über Plesk) und Spiegel auf GitHub Pages mit Canonical auf `SITE_URL`. Variablen (Einstellungen → Secrets and variables → Actions → Variables): `RATSATLAS_STADT_INFORMIERT`, `RATSATLAS_KONTAKT`, `SITE_URL`; bei Bedarf die Abhilfen aus den Hinweisen des Abrufs, `RATSATLAS_VOLLABRUF` (`ja` oder Listen wie `meetings`) und `RATSATLAS_KUERZER_ANNEHMEN` (Listen wie `organizations`), nur so lange wie nötig: `ja` und `RATSATLAS_KUERZER_ANNEHMEN` für eine Nacht (sonst jede Nacht ein Vollabruf der Vorlagen, rund 900 Anfragen), `meetings` auch dauerhaft, wenn die Stadt `modified_since` bei den Sitzungen ablehnt (etwa HTTP 401; jede Nacht alle Sitzungen, 50–200 Seiten); übergeht sie ihn nur, liest der Abruf die Sitzungen seit Runde 20 von selbst vollständig und kehrt zum inkrementellen Lauf zurück, sobald der Filter wirkt (mit dauerhaft gesetztem `meetings` entfiele dieser Versuch); der Zustand des Abrufs liegt im Zwischenspeicher des Workflows, ein Lauf an anderer Stelle wirkt nicht. Keine Zugangsdaten im Repository; Plesk zieht den Branch `deploy` (siehe [docs/PLESK.md](docs/PLESK.md)).
