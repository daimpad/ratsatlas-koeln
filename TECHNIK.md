# Ratsatlas Köln – Technik

Technische Beschreibung von Pipeline, Seite und Betrieb. Worum es inhaltlich geht, steht in der [README](README.md); Auftrag und Entscheidungen stehen in [CLAUDE.md](CLAUDE.md).

## Aufbau des Repositorys

- `pipeline/` – Abruf (`abruf.py` Abrufpolitik, `sessionnet.py` Adapter für die Kölner OParl-API), Geodaten (`geodaten.py`), Aufbereitung (`build.py`), Geokodierung (`geocode.py`, `geo.py`, `plans.py`), Akteure (`actors.py`), Themen (`topics.py`), Prozessschritte (`process.py`), Export (`export.py`, `publish.py`), Datenpaket (`paket.py`), Seiten (`seo.py`, `gebietsseiten.py`, `begriffsseite.py`, `rssseite.py`, `technikseite.py`), Kartenkacheln (`kacheln/`). Bonner Zusatzthemen (Haushalt, Themenseiten, Baustellen, Soll-Modell, Ratsassistent u. a.) bleiben im Code, sind aber über `config.ZUSATZTHEMEN` abgeschaltet.
- `site/` – statische Seite (Leaflet, `app.js`, `timeline.js`, `tour.js`); Elemente der Zusatzthemen tragen `data-funktion` und bleiben ausgeblendet.
- `data/geo/` – Kölner Stadtteile, Stadtbezirke (seit 13.11.2026 ohne Lücken und Überlappungen, siehe unten), Straßen- und Hausnummernverzeichnis (abgeleitet, dl-de/zero 2.0); `data/LICENSE-DATA.md`. Rohdaten (`data/raw/`) und Exporte (`data/export/`) sind nicht versioniert.
- `explore/` – Exploration (Phase 1): Messskripte für die OParl-API, Geodaten-Katalog, Anfrage an die Stadt.
- `inventur/` – Inventur der Bonner Kopie und Berichte der Phasen.
- `tests/` – Tests mit synthetischen Daten und einem lokalen OParl-Testserver; `tools/` – Testdaten, Seite zusammenstellen, WCAG-Prüfung.
- `.github/workflows/` – aktive Workflows; `.github/workflows-inaktiv/` – Bonner Workflows (laufen nicht).

## Pipeline

```bash
pip install -r requirements.txt
python -m pipeline fetch      # Abruf (gesperrt ohne RATSATLAS_STADT_INFORMIERT=ja; nur 23–1 Uhr)
python -m pipeline build      # SQLite data/build/allris.sqlite, Geokodierung, Akteure
python -m pipeline export     # data/export/koeln/, Audits, Stichprobe je Methode
python -m pipeline kontext    # Kennzahlen je Stadtteil, Flächen und Punkte (aus data/kontext/)
python -m pipeline ebenen     # Kartenebenen aus data/ebenen/ und export/koeln/ebenen.json
python -m pipeline package    # data/export/ratsatlas-koeln-export.zip
python -m pipeline kontext-ausschnitte   # einmalig: Zensus, BORIS, Klima, Überschwemmung, Kitas, Schulen, Haltestellen (Land, Bund)
python -m pipeline ebenen-laden          # einmalig: weitere Ebenen (Stadt, Land); je Datensatz höchstens 3 Anfragen
python -m pipeline bplan-koeln           # Bebauungspläne aus der OGC-API Bauleitplanung NRW
python -m pipeline geo-koeln  # Geodaten neu ableiten (lädt Zip-Dateien von offenedaten-koeln.de, falls nicht in data/raw/geo)
python -m pipeline geo-abdeckung        # ohne Netz: Stadtteile und Stadtbezirke in data/geo lückenlos (einmalig; danach unverändert)
python -m pipeline strukturdaten-abruf   # nur auf Freigabe (STRUKTURDATEN_ABRUF=ja, RATSATLAS_KONTAKT); höchstens 7 Anfragen
python -m pipeline strukturdaten         # ohne Netz: Zwischenspeicher → data/strukturdaten/, mit Raumabgleich
```

| Schritt | Ergebnis |
|---|---|
| `fetch` | Rohdaten im Bonner Format in `data/raw/`: `papers.jsonl`, `organizations.json`, `meetings.json` (und `meetings_roh.jsonl` mit TOPs), `legislative_terms.json`, `beratungen.jsonl` (Beratung → Sitzung und TOP, aus den Sitzungen abgeleitet); Zustand `zustand_abruf.json` (Zeitpunkte, Fortsetzungen, Zähler `sperre_verdacht` und `listenfehler`, `letzter_abbruch`, `nicht_vor` aus einem Retry-After); Abrufstatistik `data/export/abrufstatistik.tsv`; `STAND.json` mit Zeitpunkten, `abruf_fehler`, `abruf_uebersprungen` oder `abruf_hinweis` (ein vollständiger Lauf entfernt alle drei) und `abruf_warnungen` (Nebenlisten, siehe unten) |
| `build` | Tabellen Vorlage, Beratung, Sitzung, Tagesordnungspunkt, Organisation, Ort, Ortsbezug (mit Stufe, Methode, Konfidenz, Fundstelle), Einreichende, Zuständigkeit |
| `export` | je Stadtteil, Stadtbezirk und Jahr ohne Ortsbezug; `index.json`, `suche.json`, `zeit.json`, `prozesse.json`, Feeds, Kalender, GeoJSON, DCAT; stadtweite Audits `audit_*.tsv` und `stichprobe_geokodierung.tsv` (veröffentlicht nur im Datenpaket, nicht als lose Dateien auf der Seite; `tools/seite_bauen.py`, `NUR_IM_PAKET`) |
| `seo` (über `tools/seite_bauen.py`) | Gebiets-, Begriffs-, Feed- und Technikseite, `robots.txt`, `sitemap.xml`, absolute Adressen aus `SITE_URL`; Texte abgeschalteter Funktionen entfernt (`seo.ohne_abgeschaltete`, siehe unten) |

Unerwartete Feldformen (Runde 18): `build` gleicht die Vorlagen beim Einlesen an (`build.einlesen`, `data/raw` bleibt unverändert): listenwertige OParl-Felder (`consultation`, `location`, `auxiliaryFile`, `keyword`, `underDirectionOf`, `originator*`, Beziehungen; in Beratungen `organization`, `keyword`) als einzelnes Objekt werden zur Liste, `null` zur leeren Liste, in `consultation` und `location` zählen nur Objekte mit Kennung, in Listen von Adressen (Beziehungen, `originator*`, `underDirectionOf`, `relatedPaper`; in Beratungen `organization`) zählt ein eingebettetes Objekt mit seiner `id`, Einträge ohne Kennung fallen heraus, ein `mainFile`, das kein Objekt ist, gilt als fehlend, `paperType` null gilt als leere Vorlagenart und eine Vorlagenart in anderer Form (Liste, Objekt) als Text aus ihren Zeichenkettenteilen, damit die Regel für Eingaben weiter greift; sie gilt zudem als nicht erkennbare Vorlagenart, also ohne Hauskoordinate (Tabelle `paper_type_other_form`, Entscheidung 10.11.2026; alles gezählt im Log von `build`). Vorlagen ohne `reference` (fehlend, null, leer) oder mit einer `reference`, die keine Zeichenkette ist, lässt `build` aus, ohne eine Nummer zu erfinden, mit Zählung je Grund im Log (`n Vorlagen ohne Drucksachennummer ausgelassen`, `n Vorlagen mit Drucksachennummer in unerwarteter Form ausgelassen`), in der Tabelle `skipped_paper` (`reason`) und als Zeilen der Ausgabe von `check`. Ebenso ausgelassen werden Vorlagen, die die Stadt als gelöscht meldet (`deleted: true`; Grund `gelöscht`, Zeile `n Vorlagen als gelöscht gemeldet (OParl deleted) ausgelassen`; Prüfung r19b), wenn es die Kennung nicht auch ohne Löschvermerk gibt: Ihre Art ist unbekannt, und vorher verloren die mit ihnen verbundenen Vorlagen die Sperre. Für den Datenschutz bleiben ausgelassene Vorlagen Teil der Regel: Ihre Kennungen gehören zur Startmenge ohne Hauskoordinate (ohne Drucksachennummer gibt es ohnehin keine Erlaubnis), ihre Beziehungen stehen in `paper_relation`, ihr `relatedPaper` in `paper_related`, die Kennungen ihrer Ortsangaben in `skipped_location` (der Export zeigt sie nicht, weil die Vorlage fehlt). So bekommt eine Beantwortung oder Stellungnahme zu einer Eingabe oder Einwohneranfrage ohne Drucksachennummer weder im Aufbau noch nach `check.erlaubnis` eine Hauskoordinate, gleich auf welcher Seite die Beziehung steht; ebenso blendet `maske.aus_db` die Hausnummer in ihrem Titel aus, und `volltext.einwohner_kette` verortet sie nicht aus dem Volltext. Ratsfraktionen und -gruppen führt Köln in der Klasse (`classification`) „Fraktionen und Gruppen“ (Stufe 3, `organizationType` fehlt); `actors.RAT_CLASSES` nimmt sie neben den Bonner Werten auf, „Sachkundige Bürgerinnen und Bürger“ in derselben Klasse passt auf kein Muster einer Fraktion und wird nie zugeordnet.

### Abrufpolitik (CLAUDE.md 5.1)

`pipeline/abruf.py`: eine Verbindung, mindestens 2 s Abstand (`RATSATLAS_ABSTAND`, auch vor der ersten Anfrage eines Prozesses), nur im Zeitfenster 23–1 Uhr Ortszeit (`RATSATLAS_ZEITFENSTER`; laut mandari die Vorgabe der Stadt, ohne Quelle der Stadt; geprüft vor jedem Versuch und nach dem Warten auf den Abstand noch einmal unmittelbar vor dem Senden), nach 429 und 5xx Pausen von 1 min bis 3 h (`Retry-After` als Sekunden oder HTTP-Datum wird eingehalten), sofortiger Abbruch bei 401/403/404. Eine Pause muss vor dem Ende des laufenden Zeitfensters enden (gerechnet in UTC, auch über eine Zeitumstellung); sonst, und wenn `Retry-After` länger als die längste Pause oder unlesbar ist, gibt der Abruf sofort auf („aufgegeben“), statt in einer späteren Nacht weiterzumachen. Ein solcher `Retry-After` gilt über die Nacht hinaus: Bis zu seinem Ablauf steht `nicht_vor` im Zustand und jeder Lauf wird übersprungen (höchstens 30 Tage; unlesbar 7 Tage; mehr als 12 Ziffern gelten als unendlich, also 30 Tage). Lokal (ohne Freigabe, Zeitfenster, Mindestabstand, 12-Stunden-Regel und `nicht_vor`) sind nur `http://127.0.0.1`, `http://localhost` und `http://[::1]` (Prüfung des Hosts, nicht des Anfangs der Adresse). Zeitüberschreitung, Verbindungsabbruch und abgeschnittene oder unlesbare Antworten (`http.client.HTTPException`, z. B. weniger Bytes als `Content-Length`) gelten als mögliche Sperre: Abbruch ohne Wiederholung, ebenso andere TLS-Fehler (unerwartetes Ende oder Reset im Handshake). Scheitert dagegen die Zertifikatsprüfung (`CERTIFICATE_VERIFY_FAILED`), ist das vermutlich eine Einstellung der Ausführungsumgebung (CA eines Proxys; ein Zertifikat der Gegenseite oder eine Sperrseite ist nicht ausgeschlossen): Abbruch der Art `tls` ohne Wiederholung, Warnung im Workflow-Log, gezählt als Fehler und nicht als Anfrage (die HTTP-Anfrage wurde nicht gesendet), keine Nacht mit möglicher Sperre; die 12-Stunden-Regel gilt (`letzter_abbruch`), Nächte mit `tls` zählt `tlsfehler`, nach drei Nächten ohne vollständigen Lauf dazwischen sieben Tage Pause. Eine Antwort, die kein JSON ist (auch zu tief verschachtelt), gilt wie 429/5xx. Gültiges JSON in unerwarteter Form (kein Objekt, Body ohne Listen, Listenseite ohne `data` oder mit einem nicht leeren `links`, das kein Objekt ist) bricht nach einer Anfrage ohne Wiederholung ab („unlesbar“); ein leeres `links` oder `links.next` (`null`, `""`, `[]`, `{}`; SessionNet ist in PHP geschrieben) gilt als Ende der Liste. Ungültige Adressen (Zeichen außerhalb von ASCII, ein anderes Schema als http oder https, kein Host, ungültiger Port, Leerzeichen) werden nicht gesendet und nicht gezählt; der Öffner kennt nur http und https (keine Handler für FTP, Dateien und `data:`). Andere Fehler vor dem Senden (Kopfzeile mit Zeilenumbruch oder Zeichen außerhalb von Latin-1, Host nicht als IDNA kodierbar, unlesbare Proxy-Adresse) sind Einstellungs- oder Programmfehler: laut, nicht gezählt, keine Pausen; `RATSATLAS_KONTAKT` wird ohne Leerraum am Rand übernommen. Als Nacht mit möglicher Sperre zählen außerdem HTTP 401/403/429, „aufgegeben“ nach 429/5xx oder unlesbaren Antworten, Weiterleitungen und „unlesbar“; nicht dagegen Ablehnungen durch einen Proxy der Ausführungsumgebung und ungültige Adressen (sie haben die Stadt nie erreicht) sowie ein Vollabruf mit weniger als 90 % der bisherigen Objekte (Abbruch der Art `leer`). Nach jedem Abbruch außer dem Ende des Zeitfensters (auch nach einer Ablehnung durch den Proxy, einer ungültigen Adresse oder einem Programmfehler) folgt in derselben Nacht (12 h) kein weiterer Lauf (`letzter_abbruch`); nach drei Nächten mit möglicher Sperre ohne vollständigen Lauf dazwischen sieben Tage Pause. Abbrüche wegen ungültiger Folgeadressen oder Schleifen in `links.next` (ohne Fortsetzung, also jede Nacht ein Vollabruf von vorn) und wegen eines nicht angewandten Zeitfilters (Art `filter`, siehe unten) zählt `listenfehler` (Nächte, nicht Läufe): Hinweis in `STAND.json` (`abruf_hinweis`), Warnung im Workflow-Log, nach drei Nächten sieben Tage Pause. Vor der ersten Anfrage wird der Zustand geprüft: Eine unlesbare Datei oder ein unlesbarer Zeitpunkt einer Liste bricht ohne Anfrage mit Fehler ab, bei jedem Lauf, bis die Datei geprüft ist (Abhilfe in GitHub Actions: den jüngsten Zwischenspeicher `raw-…` unter Actions → Caches löschen, dann nimmt der nächste Lauf den vorigen Stand; kein automatisches Neuanlegen); ein unlesbarer, zonenloser oder künftiger Zeitpunkt des letzten Sperrverdachts, Listenfehlers oder Abbruchs gilt als „jetzt“, eine unlesbare Zahl der Nächte als drei, ein unlesbares `nicht_vor` als jetzt + 7 Tage, eines mehr als 30 Tage voraus als jetzt + 30 Tage (alles neu geschrieben und gemeldet); eine unlesbare Fortsetzung wird verworfen. Programm- und Einstellungsfehler (auch ein `RuntimeError` ohne Art, etwa `RecursionError`) zählen nicht als Sperrverdacht, sondern brechen mit Traceback ab (Abrufschritt rot, die alte Seite bleibt online) und stehen in `STAND.json`. Jeder andere Abbruch außer dem Ende des Zeitfensters und der Obergrenze je Nacht (der Abrufschritt bleibt grün) erscheint als Warnung im Workflow (`::warning::`), bei möglicher Sperre mit der Zahl der Nächte; ebenso ein übersprungener Lauf wegen der 12-Stunden-Regel, eines Retry-After oder der Pause nach drei Nächten, nicht aber ein Lauf außerhalb des Zeitfensters (Push tagsüber). Ein vollständiger Lauf entfernt `abruf_fehler`, `abruf_hinweis` und `abruf_uebersprungen`; die Seite meldet einen fehlgeschlagenen Abruf nur, wenn er nach dem letzten vollständigen liegt. Endet das Zeitfenster während eines Vollabrufs über mehrere Nächte oder erreicht er die Obergrenze je Nacht (Art `obergrenze`), ist das kein Fehler: neutraler Hinweis in `abruf_hinweis` („Obergrenze je Nacht erreicht, Fortsetzung in der nächsten Nacht“), kein Listenfehler, kein Sperrverdacht; nach der Obergrenze gilt die 12-Stunden-Regel (höchstens einmal je Nacht bis zur Grenze). Wie es weitergeht, leitet der Hinweis aus dem Zustand ab, nicht aus der abbrechenden Liste: Steht eine Fortsetzung einer Liste aus, „Fortsetzung in der nächsten Nacht“, sonst beginnt der Abruf in der nächsten Nacht erneut (ein inkrementeller Lauf speichert keine Fortsetzung). Ein inkrementeller Lauf, der länger als ein Zeitfenster braucht, beginnt so jede Nacht neu (bestehendes Verhalten, nicht umgebaut). Erreicht ein inkrementeller Lauf die Grenze je Lauf (Listenfehler `liste`), verweist der Hinweis auf `RATSATLAS_VOLLABRUF=ja` (Vollabruf, über mehrere Nächte fortgesetzt). `pages.yml` sichert den Zustand gleich nach dem Abrufschritt, auch wenn ein späterer Schritt scheitert. User-Agent `ratsatlas-koeln/0.1 (+https://github.com/daimpad/ratsatlas-koeln; <RATSATLAS_KONTAKT>)`. Listen nur über `links.next`. Parameter gehen URL-kodiert hinaus (`quote(wert, safe="")`): Köln übergeht Zeitwerte unkodiert (gleiche Seite wie ohne Filter) und wendet sie kodiert an (Stufe 2, 08.11.2026, `explore/BERICHT_phase1.md` Abschnitt 6; ersetzt für Köln die Annahme „Parameter ohne URL-Kodierung“ vom 05.11.2026, die aus anderen SessionNet-Installationen mit HTTP 404 bei kodierten Werten stammte). `links.next` gibt den Filterwert unkodiert zurück (`…?page=2&modified_since=2026-11-05T11:29:44+00:00`) und wird vor dem Folgen normalisiert: Schema, Host und Pfad bleiben, der Query-Teil wird je Parameter als `k=quote(unquote(v), safe="")` neu aufgebaut (Reihenfolge, `page` und `limit` unverändert, idempotent; `unquote`, nicht `unquote_plus`, weil Köln „+“ als wörtliches Plus liefert); zeigt `links.next` auf einen anderen Host oder Port als die Liste (ein ausdrücklicher Standardport wie `https://…:443` gilt wie keiner), wird nichts gesendet (Art `adresse`). Der Schleifenschutz und die Fortsetzung arbeiten mit der normalisierten Adresse. Offen: Ob Köln auf Seite 2 mit kodiertem Filter weiter filtert, ist ungemessen; die Abrufstatistik prüft je Lauf über alle Seiten (`filter_wirksam`, auch bei einem Abbruch aus den bis dahin gelesenen Seiten), und ein inkrementeller Lauf prüft jede Seite: Enthält sie Objekte mit lesbarem `modified` vor `modified_since` (die Überlappung von einem Tag ist dort schon abgezogen; Löschungen mit `deleted: true` ausgenommen, sie können ein altes `modified` tragen), wendet der Server den Filter nicht an. Bei den Vorlagen bricht der Lauf dann nach dieser Seite ab (Art `filter`, „Zeitfilter auf Seite N nicht angewandt“ in Abrufstatistik und `STAND.json`; zählt wie ein Listenfehler, nach drei Nächten sieben Tage Pause), statt bis zum Fensterende die ganze Liste zu lesen; Seite 1 der Vorlagen löst das in Kölner Form nicht aus (Stufe 2: kodiert keine Vorlage unter der Grenze). Bei den Sitzungen liest der Lauf die Liste dann in derselben Nacht vollständig (Entscheidung 10.11.2026, umgesetzt in Runde 20; `sessionnet._abruf_liste` mit `voll_ohne_filter`): neu ab Seite 1 ohne `modified_since`, also eine Anfrage mehr, statt `links.next` der gefilterten Seite weiter zu folgen. Begründung: Ob Köln den Filter auf Folgeseiten ebenso übergeht und ob die Seitengrenzen mit und ohne Filter gleich sind, ist ungemessen; ein „Vollabruf“, auf dessen Folgeseiten der Filter doch wirkte, ersetzte den Stand unbemerkt durch einen Teil (unter 90 % fiele es auf, darüber nicht). Der Neustart sendet dieselben Anfragen wie ein Vollabruf der Sitzungen (`RATSATLAS_VOLLABRUF=meetings`) und gilt wie einer: 90-%-Regel gegenüber dem Stand (Art `leer`: Abbruch des Laufs, Stand bleibt, jede Nacht erneut; Abhilfe `RATSATLAS_KUERZER_ANNEHMEN=meetings`; seit der Prüfung r20 nennt die Meldung in `STAND.json` den Anlass „vollständiges Lesen nach nicht angewandtem Zeitfilter“ und diese Abhilfe, die Abrufstatistik Seiten und Objekte), der Stand wird ersetzt, nicht zusammengeführt (eine in der Quelle entfernte Sitzung fehlt danach); beenden ihn das Zeitfenster oder die Obergrenze je Lauf, folgt die Fortsetzung in der nächsten Nacht. Die Seiten mit Zeitfilter zählen zur Grenze je Lauf (`liste(…, im_lauf=…)`), nicht zu den Seiten des Vollabrufs (Gesamtgrenze, `meetings_fortsetzung.seiten`); ist die Grenze schon mit ihnen erreicht (Befund auf der letzten erlaubten Seite), folgt keine Anfrage mehr (Art `obergrenze`, ohne Fortsetzung, die nächste Nacht beginnt wieder mit Zeitfilter; Prüfung r20: vorher eine Seite ohne Filter zu viel, weil `liste()` vor der ersten Seite die Seitengröße nicht kennt). Jede Nacht, nicht jeder Lauf (Prüfung r20): Ein weiterer Lauf in derselben Nacht (Push auf `main` im Zeitfenster, den die concurrency-Gruppe „pages“ hinter den Nachtlauf reiht, Knopfdruck oder ein neu gestarteter Job; nach einem vollständigen Lauf greift die 12-Stunden-Regel nicht) liest die Sitzungen nicht noch einmal vollständig, wenn sie in dieser Nacht schon gelesen sind (Zustand `meetings`, Beginn des letzten erfolgreichen Lesens, oder `meetings` in `STAND.json`, sein Ende, auch das einer Fortsetzung, die erst in dieser Nacht fertig wurde (Prüfung r20n; vorher galten die Sitzungen nach einer Fortsetzung als in der Vornacht gelesen und ein weiterer Lauf las sie noch einmal vollständig); der spätere dieser Zeitpunkte, weniger als 12 Stunden zurück, ein künftiger zählt nicht; `sessionnet._in_dieser_nacht_gelesen`, nicht für lokale Testserver wie die 12-Stunden-Regel): Mit dem Vermerk `meetings_ohne_zeitfilter` aus dem früheren Lauf ohne Anfrage (wie bis Runde 19), sonst nach dem Befund auf den k Seiten mit Zeitfilter (etwa nach dem ersten Vollabruf oder `RATSATLAS_VOLLABRUF=meetings` in derselben Nacht); letzter gültiger Stand, `meetings.json` und ihr Zeitpunkt unverändert, keine Warnung in `STAND.json`, Zeile mit `ergebnis` „übersprungen: … in dieser Nacht schon gelesen (zuletzt …) …“ in der Abrufstatistik (`modus` „übersprungen“ bzw. „inkrementell“), Meldung im Log (`sessionnet._schon_gelesen`). Ohne diese Regel kostete jeder weitere Lauf der Nacht noch einmal k + ⌈M / 100⌉ Anfragen. Kein Listenfehler, keine Pause, keine Warnung in `abruf_warnungen` (die Sitzungen sind aktualisiert); Warnung „Zeitfilter bei Sitzungen nicht angewandt, Sitzungen vollständig gelesen (N Seiten ohne modified_since nach k mit Zeitfilter); Befund: …“ im Log und als `ok; …` in der Abrufstatistik (`modus` „voll, Zeitfilter nicht angewandt“, `filter_wirksam` „nein (… ältere)“ aus den Seiten mit Zeitfilter, `anfragen` mit ihnen). Jede Nacht beginnt die Liste wieder mit Zeitfilter: Wendet der Server ihn wieder an, bleibt der Lauf ohne Zutun inkrementell. Ob Köln `modified_since` bei den Sitzungen anwendet, ist ungemessen; die Abrufstatistik zeigt es nach der ersten inkrementellen Nacht. Mehranfragen, solange der Server den Filter übergeht: je Nacht ⌈M / 100⌉ Seiten ohne Filter zusätzlich zu den k Seiten mit Filter bis zum Befund (meist k = 1; M Sitzungen insgesamt, ungemessen, nach dem ersten Vollabruf in der Spalte `objekte` der Zeile `meetings`); bei 5 000 bis 20 000 Sitzungen (Schätzung wie unten bei den Variablen, ungemessen) 51 bis 201 Anfragen je Nacht, mit 2 s Abstand und 3 bis 6 s Antwortzeit rund 4 bis 27 Minuten des Zeitfensters (Schätzung: Stufe 2 maß für die erste Sitzungsseite mit 25 Sitzungen 19,6 KB in 1,46 s, für 100 Vorlagen 5,07 s; 100 Sitzungen je Seite ungemessen); ein weiterer Lauf derselben Nacht 0 bzw. k Anfragen (siehe oben). Bis Runde 19 las der Lauf nach dem Befund keine Sitzungen mehr (Folgenächte ohne Anfrage), die Sitzungen blieben also bis zu einem Vollabruf veraltet. Die Organisationen ruft der Abruf immer ohne Zeitfilter und vollständig ab, auch im inkrementellen Lauf, ohne Filterprüfung: eine kleine Liste (den Umfang misst Stufe 3), und Münster lehnt `modified_since` bei `organization` mit HTTP 401 ab (`explore/ergebnisse/sessionnet_befunde.tsv`; mandari ruft sie dann ohne Filter ab). Weil sie vor den Vorlagen kommen, beendet ein Vollabruf der Organisationen unter 90 % des Stands (Art `leer`) nur diese Liste (letzter gültiger Stand, Warnung in `abruf_warnungen`), statt jede Nacht die Vorlagen zu blockieren. Offen: Eine Antwort HTTP 401 auf einen Zeitfilter wie in Münster wertet die Pipeline heute als Nacht mit möglicher Sperre (Art `http`); bei den Sitzungen hieße das jede Nacht einen Abbruch auf ihrer ersten Seite (die Vorlagen sind dann schon gelesen, die Beratungen nicht abgeleitet) und nach drei Nächten sieben Tage Pause, auch für die Vorlagen (nicht umgebaut; vor der Freigabe messen). Ebenfalls ungemessen: `limit=100` für `meetings` und `organizations` (Stufe 2 nur mit 25 je Seite, Sitzungen Seite 1: 19,6 KB in 1,46 s); Messung in einer späteren Stufe. Seitengröße `limit=100` (`RATSATLAS_LIMIT`, Stufe 2: 100 Vorlagen in 5,07 s, `next` mit `limit=100`) an der ersten Listenadresse; trägt `links.next` ihn nicht, wird er angehängt. Ehrenfeld, Ränder aus, Ausschnitt von 166 320 Bildpunkten: mit `smoothFactor` 1 sind es 24 bzw. 5 Lückenpunkte und 875 bzw. 507 doppelt gedeckte Bildpunkte, mit 0 keine). *Klassen nach Quantilen* (Vorgabe): Grenzen sind die Werte an Index ⌊q·(n−1)⌋ der aufsteigend sortierten Werte des gewählten Jahres auf dieser Raumebene für q = 0,2, 0,4, 0,6, 0,8 (wie die übrigen Flächenfarben in `app.js`), gerundet auf eine Nachkommastelle (zwei, wenn das mehr Grenzen trennt); gleiche Grenzen fallen zusammen, Grenzen, die nicht über dem gerundeten Minimum liegen, entfallen. Ein Wert, der gerundet auf der Grenze liegt, gehört zur oberen Klasse; so stimmen Zahl, Farbe und Legende überein, und keine Klasse bleibt leer (Prüfung 10.11.2026: vorher lagen rund 3 % der Werte in der Klasse unter ihrer angezeigten Zahl). *Feste Grenzen über alle Jahre*: dieselbe Rechnung über die Werte aller Jahre der Raumebene, damit eine Farbe in jedem Jahr dasselbe bedeutet. | Datei | Zeit | Aufgabe |
|---|---|---|
| `pages.yml` | täglich 22:10 UTC, bei Push auf `main`, auf Knopfdruck | Abruf (gesperrt bis zur Repository-Variable `RATSATLAS_STADT_INFORMIERT=ja`), Aufbereitung, Export, Datenpaket; Branch `deploy` (Hauptadresse über Plesk) und Spiegel auf GitHub Pages mit Canonical auf `SITE_URL`. | `kacheln.yml` | vierteljährlich, auf Knopfdruck, bei Pull Requests zu `pipeline/kacheln/` | graue Kartenkacheln aus OSM (Protomaps-Ausschnitt Köln) in den Branch `kacheln`, danach `pages.yml` |
| `tests.yml` | Pull Requests, Push auf `main` | Tests, Syntax der Seite |
| `live.yml` | auf Knopfdruck (nach der Einrichtung in Plesk täglich) | Hauptadresse und Spiegel erreichbar, aktueller Stand, Canonical, Kopfzeilen |

Variablen (Einstellungen → Secrets and variables → Actions → Variables): `RATSATLAS_STADT_INFORMIERT`, `RATSATLAS_KONTAKT`, `SITE_URL`; bei Bedarf die Abhilfen aus den Hinweisen des Abrufs, `RATSATLAS_VOLLABRUF` (`ja` oder Listen wie `meetings`) und `RATSATLAS_KUERZER_ANNEHMEN` (Listen wie `organizations`), nur so lange wie nötig: `ja` und `RATSATLAS_KUERZER_ANNEHMEN` für eine Nacht (sonst jede Nacht ein Vollabruf der Vorlagen, rund 900 Anfragen), `meetings` auch dauerhaft, wenn die Stadt `modified_since` bei den Sitzungen ablehnt (etwa HTTP 401; jede Nacht alle Sitzungen, 50–200 Seiten); übergeht sie ihn nur, liest der Abruf die Sitzungen seit Runde 20 von selbst vollständig und kehrt zum inkrementellen Lauf zurück, sobald der Filter wirkt (mit dauerhaft gesetztem `meetings` entfiele dieser Versuch); der Zustand des Abrufs liegt im Zwischenspeicher des Workflows, ein Lauf an anderer Stelle wirkt nicht. Abstand, Zeitfenster, Seitengröße und Grenzen je Nacht sind nicht über Variablen einstellbar. Keine Zugangsdaten im Repository; Plesk zieht den Branch `deploy` (siehe [docs/PLESK.md](docs/PLESK.md)).

Branch `deploy`: flacher Klon, ein Commit je Lauf, die Historie wächst um die Änderungen (Plesk-Git räumt mit `git gc` auf); ohne Datenpaket und, weil GitHub höchstens 100 MB je Datei annimmt (Generalprobe: `audit_prozess.tsv` 98,3 MB; die Audits liegen seit Runde 19 nur im Datenpaket, siehe unten), ohne jede Datei über 95 MB (95 000 000 Byte): Sie bleibt mit `::warning::` (Pfad, Größe) im Log draußen, liegt im Datenpaket und auf dem Spiegel GitHub Pages, und der Push läuft weiter (auf der Hauptadresse fehlt die Datei dann).
