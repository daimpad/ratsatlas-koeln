# Ratsatlas Köln – Technik

Technische Beschreibung von Pipeline, Seite und Betrieb. Worum es inhaltlich geht, steht in der [README](README.md); Auftrag und Entscheidungen stehen in [CLAUDE.md](CLAUDE.md).

## Aufbau des Repositorys

- `pipeline/` – Abruf (`abruf.py` Abrufpolitik, `sessionnet.py` Adapter für die Kölner OParl-API), Geodaten (`geodaten.py`), Aufbereitung (`build.py`), Geokodierung (`geocode.py`, `geo.py`, `plans.py`), Akteure (`actors.py`), Themen (`topics.py`), Prozessschritte (`process.py`), Export (`export.py`, `publish.py`), Datenpaket (`paket.py`), Seiten (`seo.py`, `gebietsseiten.py`, `begriffsseite.py`, `rssseite.py`, `technikseite.py`), Kartenkacheln (`kacheln/`). Bonner Zusatzthemen (Haushalt, Themenseiten, Baustellen, Soll-Modell, Ratsassistent u. a.) bleiben im Code, sind aber über `config.ZUSATZTHEMEN` abgeschaltet.
- `site/` – statische Seite (Leaflet, `app.js`, `timeline.js`, `tour.js`); Elemente der Zusatzthemen tragen `data-funktion` und bleiben ausgeblendet.
- `data/geo/` – Kölner Stadtteile, Stadtbezirke, Straßen- und Hausnummernverzeichnis (abgeleitet, dl-de/zero 2.0); `data/LICENSE-DATA.md`. Rohdaten (`data/raw/`) und Exporte (`data/export/`) sind nicht versioniert.
- `explore/` – Exploration (Phase 1): Messskripte für die OParl-API, Geodaten-Katalog, Anfrage an die Stadt.
- `inventur/` – Inventur der Bonner Kopie und Berichte der Phasen.
- `tests/` – Tests mit synthetischen Daten und einem lokalen OParl-Testserver; `tools/` – Testdaten, Seite zusammenstellen, WCAG-Prüfung.
- `.github/workflows/` – aktive Workflows; `.github/workflows-inaktiv/` – Bonner Workflows (laufen nicht).

## Pipeline

```bash
pip install -r requirements.txt
python -m pipeline fetch      # Abruf (gesperrt ohne RATSATLAS_STADT_INFORMIERT=ja; nur 23–1 Uhr)
python -m pipeline build      # SQLite data/build/allris.sqlite, Geokodierung, Akteure
python -m pipeline export     # data/export/koeln/, Audits, Stichprobe je Methode
python -m pipeline kontext    # Kennzahlen je Stadtteil, Flächen und Punkte (aus data/kontext/)
python -m pipeline ebenen     # Kartenebenen aus data/ebenen/ und export/koeln/ebenen.json
python -m pipeline package    # data/export/ratsatlas-koeln-export.zip
python -m pipeline kontext-ausschnitte   # einmalig: Zensus, BORIS, Klima, Überschwemmung, Kitas, Schulen, Haltestellen (Land, Bund)
python -m pipeline ebenen-laden          # einmalig: weitere Ebenen (Stadt, Land); je Datensatz höchstens 3 Anfragen
python -m pipeline bplan-koeln           # Bebauungspläne aus der OGC-API Bauleitplanung NRW
python -m pipeline geo-koeln  # Geodaten neu ableiten (lädt Zip-Dateien von offenedaten-koeln.de, falls nicht in data/raw/geo)
```

| Schritt | Ergebnis |
|---|---|
| `fetch` | Rohdaten im Bonner Format in `data/raw/`: `papers.jsonl`, `organizations.json`, `meetings.json` (und `meetings_roh.jsonl` mit TOPs), `legislative_terms.json`, `beratungen.jsonl` (Beratung → Sitzung und TOP, aus den Sitzungen abgeleitet); Zustand `zustand_abruf.json` (Zeitpunkte, Fortsetzungen, Zähler `sperre_verdacht` und `listenfehler`, `letzter_abbruch`, `nicht_vor` aus einem Retry-After); Abrufstatistik `data/export/abrufstatistik.tsv`; `STAND.json` mit Zeitpunkten, `abruf_fehler`, `abruf_uebersprungen` oder `abruf_hinweis` (ein vollständiger Lauf entfernt alle drei) und `abruf_warnungen` (Nebenlisten, siehe unten) |
| `build` | Tabellen Vorlage, Beratung, Sitzung, Tagesordnungspunkt, Organisation, Ort, Ortsbezug (mit Stufe, Methode, Konfidenz, Fundstelle), Einreichende, Zuständigkeit |
| `export` | je Stadtteil, Stadtbezirk und Jahr ohne Ortsbezug; `index.json`, `suche.json`, `zeit.json`, `prozesse.json`, Feeds, Kalender, GeoJSON, DCAT; stadtweite Audits `audit_*.tsv` und `stichprobe_geokodierung.tsv` (veröffentlicht nur im Datenpaket, nicht als lose Dateien auf der Seite; `tools/seite_bauen.py`, `NUR_IM_PAKET`) |
| `seo` (über `tools/seite_bauen.py`) | Gebiets-, Begriffs-, Feed- und Technikseite, `robots.txt`, `sitemap.xml`, absolute Adressen aus `SITE_URL`; Texte abgeschalteter Funktionen entfernt (`seo.ohne_abgeschaltete`, siehe unten) |

Unerwartete Feldformen (Runde 18): `build` gleicht die Vorlagen beim Einlesen an (`build.einlesen`, `data/raw` bleibt unverändert): listenwertige OParl-Felder (`consultation`, `location`, `auxiliaryFile`, `keyword`, `underDirectionOf`, `originator*`, Beziehungen; in Beratungen `organization`, `keyword`) als einzelnes Objekt werden zur Liste, `null` zur leeren Liste, in `consultation` und `location` zählen nur Objekte mit Kennung, in Listen von Adressen (Beziehungen, `originator*`, `underDirectionOf`, `relatedPaper`; in Beratungen `organization`) zählt ein eingebettetes Objekt mit seiner `id`, Einträge ohne Kennung fallen heraus, ein `mainFile`, das kein Objekt ist, gilt als fehlend, `paperType` null gilt als leere Vorlagenart und eine Vorlagenart in anderer Form (Liste, Objekt) als Text aus ihren Zeichenkettenteilen, damit die Regel für Eingaben weiter greift; sie gilt zudem als nicht erkennbare Vorlagenart, also ohne Hauskoordinate (Tabelle `paper_type_other_form`, Entscheidung 10.11.2026; alles gezählt im Log von `build`). Vorlagen ohne `reference` (fehlend, null, leer) oder mit einer `reference`, die keine Zeichenkette ist, lässt `build` aus, ohne eine Nummer zu erfinden, mit Zählung je Grund im Log (`n Vorlagen ohne Drucksachennummer ausgelassen`, `n Vorlagen mit Drucksachennummer in unerwarteter Form ausgelassen`), in der Tabelle `skipped_paper` (`reason`) und als Zeilen der Ausgabe von `check`. Ebenso ausgelassen werden Vorlagen, die die Stadt als gelöscht meldet (`deleted: true`; Grund `gelöscht`, Zeile `n Vorlagen als gelöscht gemeldet (OParl deleted) ausgelassen`; Prüfung r19b), wenn es die Kennung nicht auch ohne Löschvermerk gibt: Ihre Art ist unbekannt, und vorher verloren die mit ihnen verbundenen Vorlagen die Sperre. Für den Datenschutz bleiben ausgelassene Vorlagen Teil der Regel: Ihre Kennungen gehören zur Startmenge ohne Hauskoordinate (ohne Drucksachennummer gibt es ohnehin keine Erlaubnis), ihre Beziehungen stehen in `paper_relation`, ihr `relatedPaper` in `paper_related`, die Kennungen ihrer Ortsangaben in `skipped_location` (der Export zeigt sie nicht, weil die Vorlage fehlt). So bekommt eine Beantwortung oder Stellungnahme zu einer Eingabe oder Einwohneranfrage ohne Drucksachennummer weder im Aufbau noch nach `check.erlaubnis` eine Hauskoordinate, gleich auf welcher Seite die Beziehung steht; ebenso blendet `maske.aus_db` die Hausnummer in ihrem Titel aus, und `volltext.einwohner_kette` verortet sie nicht aus dem Volltext. Ratsfraktionen und -gruppen führt Köln in der Klasse (`classification`) „Fraktionen und Gruppen“ (Stufe 3, `organizationType` fehlt); `actors.RAT_CLASSES` nimmt sie neben den Bonner Werten auf, „Sachkundige Bürgerinnen und Bürger“ in derselben Klasse passt auf kein Muster einer Fraktion und wird nie zugeordnet.

### Abrufpolitik (CLAUDE.md 5.1)

`pipeline/abruf.py`: eine Verbindung, mindestens 2 s Abstand (`RATSATLAS_ABSTAND`, auch vor der ersten Anfrage eines Prozesses), nur im Zeitfenster 23–1 Uhr Ortszeit (`RATSATLAS_ZEITFENSTER`; laut mandari die Vorgabe der Stadt, ohne Quelle der Stadt; geprüft vor jedem Versuch und nach dem Warten auf den Abstand noch einmal unmittelbar vor dem Senden), nach 429 und 5xx Pausen von 1 min bis 3 h (`Retry-After` als Sekunden oder HTTP-Datum wird eingehalten), sofortiger Abbruch bei 401/403/404. Eine Pause muss vor dem Ende des laufenden Zeitfensters enden (gerechnet in UTC, auch über eine Zeitumstellung); sonst, und wenn `Retry-After` länger als die längste Pause oder unlesbar ist, gibt der Abruf sofort auf („aufgegeben“), statt in einer späteren Nacht weiterzumachen. Ein solcher `Retry-After` gilt über die Nacht hinaus: Bis zu seinem Ablauf steht `nicht_vor` im Zustand und jeder Lauf wird übersprungen (höchstens 30 Tage; unlesbar 7 Tage; mehr als 12 Ziffern gelten als unendlich, also 30 Tage). Lokal (ohne Freigabe, Zeitfenster, Mindestabstand, 12-Stunden-Regel und `nicht_vor`) sind nur `http://127.0.0.1`, `http://localhost` und `http://[::1]` (Prüfung des Hosts, nicht des Anfangs der Adresse). Zeitüberschreitung, Verbindungsabbruch und abgeschnittene oder unlesbare Antworten (`http.client.HTTPException`, z. B. weniger Bytes als `Content-Length`) gelten als mögliche Sperre: Abbruch ohne Wiederholung, ebenso andere TLS-Fehler (unerwartetes Ende oder Reset im Handshake). Scheitert dagegen die Zertifikatsprüfung (`CERTIFICATE_VERIFY_FAILED`), ist das vermutlich eine Einstellung der Ausführungsumgebung (CA eines Proxys; ein Zertifikat der Gegenseite oder eine Sperrseite ist nicht ausgeschlossen): Abbruch der Art `tls` ohne Wiederholung, Warnung im Workflow-Log, gezählt als Fehler und nicht als Anfrage (die HTTP-Anfrage wurde nicht gesendet), keine Nacht mit möglicher Sperre; die 12-Stunden-Regel gilt (`letzter_abbruch`), Nächte mit `tls` zählt `tlsfehler`, nach drei Nächten ohne vollständigen Lauf dazwischen sieben Tage Pause. Eine Antwort, die kein JSON ist (auch zu tief verschachtelt), gilt wie 429/5xx. Gültiges JSON in unerwarteter Form (kein Objekt, Body ohne Listen, Listenseite ohne `data` oder mit einem nicht leeren `links`, das kein Objekt ist) bricht nach einer Anfrage ohne Wiederholung ab („unlesbar“); ein leeres `links` oder `links.next` (`null`, `""`, `[]`, `{}`; SessionNet ist in PHP geschrieben) gilt als Ende der Liste. Ungültige Adressen (Zeichen außerhalb von ASCII, ein anderes Schema als http oder https, kein Host, ungültiger Port, Leerzeichen) werden nicht gesendet und nicht gezählt; der Öffner kennt nur http und https (keine Handler für FTP, Dateien und `data:`). Andere Fehler vor dem Senden (Kopfzeile mit Zeilenumbruch oder Zeichen außerhalb von Latin-1, Host nicht als IDNA kodierbar, unlesbare Proxy-Adresse) sind Einstellungs- oder Programmfehler: laut, nicht gezählt, keine Pausen; `RATSATLAS_KONTAKT` wird ohne Leerraum am Rand übernommen. Als Nacht mit möglicher Sperre zählen außerdem HTTP 401/403/429, „aufgegeben“ nach 429/5xx oder unlesbaren Antworten, Weiterleitungen und „unlesbar“; nicht dagegen Ablehnungen durch einen Proxy der Ausführungsumgebung und ungültige Adressen (sie haben die Stadt nie erreicht) sowie ein Vollabruf mit weniger als 90 % der bisherigen Objekte (Abbruch der Art `leer`). Nach jedem Abbruch außer dem Ende des Zeitfensters (auch nach einer Ablehnung durch den Proxy, einer ungültigen Adresse oder einem Programmfehler) folgt in derselben Nacht (12 h) kein weiterer Lauf (`letzter_abbruch`); nach drei Nächten mit möglicher Sperre ohne vollständigen Lauf dazwischen sieben Tage Pause. Abbrüche wegen ungültiger Folgeadressen oder Schleifen in `links.next` (ohne Fortsetzung, also jede Nacht ein Vollabruf von vorn) und wegen eines nicht angewandten Zeitfilters (Art `filter`, siehe unten) zählt `listenfehler` (Nächte, nicht Läufe): Hinweis in `STAND.json` (`abruf_hinweis`), Warnung im Workflow-Log, nach drei Nächten sieben Tage Pause. Vor der ersten Anfrage wird der Zustand geprüft: Eine unlesbare Datei oder ein unlesbarer Zeitpunkt einer Liste bricht ohne Anfrage mit Fehler ab, bei jedem Lauf, bis die Datei geprüft ist (Abhilfe in GitHub Actions: den jüngsten Zwischenspeicher `raw-…` unter Actions → Caches löschen, dann nimmt der nächste Lauf den vorigen Stand; kein automatisches Neuanlegen); ein unlesbarer, zonenloser oder künftiger Zeitpunkt des letzten Sperrverdachts, Listenfehlers oder Abbruchs gilt als „jetzt“, eine unlesbare Zahl der Nächte als drei, ein unlesbares `nicht_vor` als jetzt + 7 Tage, eines mehr als 30 Tage voraus als jetzt + 30 Tage (alles neu geschrieben und gemeldet); eine unlesbare Fortsetzung wird verworfen. Programm- und Einstellungsfehler (auch ein `RuntimeError` ohne Art, etwa `RecursionError`) zählen nicht als Sperrverdacht, sondern brechen mit Traceback ab (Abrufschritt rot, die alte Seite bleibt online) und stehen in `STAND.json`. Jeder andere Abbruch außer dem Ende des Zeitfensters und der Obergrenze je Nacht (der Abrufschritt bleibt grün) erscheint als Warnung im Workflow (`::warning::`), bei möglicher Sperre mit der Zahl der Nächte; ebenso ein übersprungener Lauf wegen der 12-Stunden-Regel, eines Retry-After oder der Pause nach drei Nächten, nicht aber ein Lauf außerhalb des Zeitfensters (Push tagsüber). Ein vollständiger Lauf entfernt `abruf_fehler`, `abruf_hinweis` und `abruf_uebersprungen`; die Seite meldet einen fehlgeschlagenen Abruf nur, wenn er nach dem letzten vollständigen liegt. Endet das Zeitfenster während eines Vollabrufs über mehrere Nächte oder erreicht er die Obergrenze je Nacht (Art `obergrenze`), ist das kein Fehler: neutraler Hinweis in `abruf_hinweis` („Obergrenze je Nacht erreicht, Fortsetzung in der nächsten Nacht“), kein Listenfehler, kein Sperrverdacht; nach der Obergrenze gilt die 12-Stunden-Regel (höchstens einmal je Nacht bis zur Grenze). Wie es weitergeht, leitet der Hinweis aus dem Zustand ab, nicht aus der abbrechenden Liste: Steht eine Fortsetzung einer Liste aus, „Fortsetzung in der nächsten Nacht“, sonst beginnt der Abruf in der nächsten Nacht erneut (ein inkrementeller Lauf speichert keine Fortsetzung). Ein inkrementeller Lauf, der länger als ein Zeitfenster braucht, beginnt so jede Nacht neu (bestehendes Verhalten, nicht umgebaut). Erreicht ein inkrementeller Lauf die Grenze je Lauf (Listenfehler `liste`), verweist der Hinweis auf `RATSATLAS_VOLLABRUF=ja` (Vollabruf, über mehrere Nächte fortgesetzt). `pages.yml` sichert den Zustand gleich nach dem Abrufschritt, auch wenn ein späterer Schritt scheitert. User-Agent `ratsatlas-koeln/0.1 (+https://github.com/daimpad/ratsatlas-koeln; <RATSATLAS_KONTAKT>)`. Listen nur über `links.next`. Parameter gehen URL-kodiert hinaus (`quote(wert, safe="")`): Köln übergeht Zeitwerte unkodiert (gleiche Seite wie ohne Filter) und wendet sie kodiert an (Stufe 2, 08.11.2026, `explore/BERICHT_phase1.md` Abschnitt 6; ersetzt für Köln die Annahme „Parameter ohne URL-Kodierung“ vom 05.11.2026, die aus anderen SessionNet-Installationen mit HTTP 404 bei kodierten Werten stammte). `links.next` gibt den Filterwert unkodiert zurück (`…?page=2&modified_since=2026-11-05T11:29:44+00:00`) und wird vor dem Folgen normalisiert: Schema, Host und Pfad bleiben, der Query-Teil wird je Parameter als `k=quote(unquote(v), safe="")` neu aufgebaut (Reihenfolge, `page` und `limit` unverändert, idempotent; `unquote`, nicht `unquote_plus`, weil Köln „+“ als wörtliches Plus liefert); zeigt `links.next` auf einen anderen Host oder Port als die Liste (ein ausdrücklicher Standardport wie `https://…:443` gilt wie keiner), wird nichts gesendet (Art `adresse`). Der Schleifenschutz und die Fortsetzung arbeiten mit der normalisierten Adresse. Offen: Ob Köln auf Seite 2 mit kodiertem Filter weiter filtert, ist ungemessen; die Abrufstatistik prüft je Lauf über alle Seiten (`filter_wirksam`, auch bei einem Abbruch aus den bis dahin gelesenen Seiten), und ein inkrementeller Lauf prüft jede Seite: Enthält sie Objekte mit lesbarem `modified` vor `modified_since` (die Überlappung von einem Tag ist dort schon abgezogen; Löschungen mit `deleted: true` ausgenommen, sie können ein altes `modified` tragen), wendet der Server den Filter nicht an. Bei den Vorlagen bricht der Lauf dann nach dieser Seite ab (Art `filter`, „Zeitfilter auf Seite N nicht angewandt“ in Abrufstatistik und `STAND.json`; zählt wie ein Listenfehler, nach drei Nächten sieben Tage Pause), statt bis zum Fensterende die ganze Liste zu lesen; Seite 1 der Vorlagen löst das in Kölner Form nicht aus (Stufe 2: kodiert keine Vorlage unter der Grenze). Bei den Sitzungen endet nur diese Liste (keine weiteren Seiten): Die Sitzungen bleiben auf dem letzten gültigen Stand (nicht zusammengeführt, Zeitpunkt nicht weitergesetzt), Warnung „Zeitfilter bei Sitzungen nicht angewandt, Sitzungen nicht aktualisiert“ in `STAND.json` (`abruf_warnungen`) und Abrufstatistik (`warnung: …`, `filter_wirksam` „nein“); kein Listenfehler, keine Pause, der Lauf gilt als vollständig. Ob Köln `modified_since` bei den Sitzungen anwendet, ist ungemessen (offen: vor der Freigabe des nächtlichen Abrufs mit einer Anfrage messen). Die Organisationen ruft der Abruf immer ohne Zeitfilter und vollständig ab, auch im inkrementellen Lauf, ohne Filterprüfung: eine kleine Liste (den Umfang misst Stufe 3), und Münster lehnt `modified_since` bei `organization` mit HTTP 401 ab (`explore/ergebnisse/sessionnet_befunde.tsv`; mandari ruft sie dann ohne Filter ab). Weil sie vor den Vorlagen kommen, beendet ein Vollabruf der Organisationen unter 90 % des Stands (Art `leer`) nur diese Liste (letzter gültiger Stand, Warnung wie bei den Sitzungen), statt jede Nacht die Vorlagen zu blockieren. Offen: Eine Antwort HTTP 401 auf einen Zeitfilter wie in Münster wertet die Pipeline heute als Nacht mit möglicher Sperre (Art `http`); bei den Sitzungen hieße das jede Nacht einen Abbruch auf ihrer ersten Seite (die Vorlagen sind dann schon gelesen, die Beratungen nicht abgeleitet) und nach drei Nächten sieben Tage Pause, auch für die Vorlagen (nicht umgebaut; vor der Freigabe messen). Ebenfalls ungemessen: `limit=100` für `meetings` und `organizations` (Stufe 2 nur mit 25 je Seite, Sitzungen Seite 1: 19,6 KB in 1,46 s); Messung in einer späteren Stufe. Seitengröße `limit=100` (`RATSATLAS_LIMIT`, Stufe 2: 100 Vorlagen in 5,07 s, `next` mit `limit=100`) an der ersten Listenadresse; trägt `links.next` ihn nicht, wird er angehängt. Alle seitenbezogenen Grenzen gelten in Objekten und werden mit der tatsächlichen Seitengröße des Laufs (größte gelesene Seite) in Seiten umgerechnet: höchstens `RATSATLAS_MAX_OBJEKTE` (100 000, bei 100 je Seite 1000 Seiten) je Liste und Lauf als Höflichkeitsgrenze je Nacht (höchstens rund 1000 Anfragen je Liste und Nacht): Ein Vollabruf endet dort wie am Ende des Zeitfensters (Art `obergrenze`) und wird in der nächsten Nacht fortgesetzt (die Grenze zählt dort neu), sofern der Lauf über die wiederholte Seite einer Fortsetzung hinaus neue Objekte gelesen hat (sonst Abbruch `liste`: die Fortsetzung käme nie voran); ein inkrementeller Lauf bricht dort als Listenfehler ab (Art `liste`). Werte von `RATSATLAS_MAX_OBJEKTE` unter (⌈1000 / g⌉ + 2) · g mit g = `RATSATLAS_LIMIT` (zwei Seiten plus die größte Seitenverschiebung von 1000 Objekten, aufgerundet auf Seiten; bei 100 je Seite 1200, bei 150 1350; leeres `RATSATLAS_LIMIT` gerechnet wie 100; also auch 0 und negative) lehnt der Abruf vor der ersten Anfrage als Einstellungsfehler ab (laut, kein Sperrverdacht), ebenso ein `RATSATLAS_LIMIT`, das keine positive ganze Zahl ist. Annahme: Der Server liefert g Objekte je Seite wie verlangt. Über alle Fortsetzungen eines Vollabrufs höchstens 600 000 Objekte (`ABRUF_MAX_OBJEKTE_GESAMT`, Schleifenschutz; ein Vollabruf mit bis zu 500 000 Objekten je Liste wird so sicher fertig; geprüft vor der Grenze je Lauf und ab der zweiten Anfrage eines Laufs, sonst Abbruch wie bei einer Schleife). Das ist eine Abwägung: Eine Liste, die endlos neue Kennungen erzeugt, erkennt diese Grenze erst nach rund sechs Nächten (bis zu 1000 Seiten zu 100 je Nacht, also bis zu rund 6000 Anfragen); eine engere Grenze gefährdete den Vollabruf großer Listen (bis 500 000 Objekte). Abbruch auch bei Seiten ohne neue Kennungen. Kapazität je Nacht (Start 23:10 Uhr, im Sommer 0:10 Uhr; Ende 1 Uhr; rund 108 bzw. 48 Minuten nach der Einrichtung des Laufs): mit 100 je Seite rund 7 s je Seite (5,1 s Antwort plus 2 s Abstand), also rund 900 Seiten oder 90 000 Objekte (im Sommer rund 400 Seiten, 40 000 Objekte); bei schnellen Antworten (3 s) wären es rund 1300 Seiten, die Obergrenze je Nacht beendet den Lauf dann nach 1000 Seiten; mit 25 je Seite (2,3–2,8 s Antwort) rund 1400 Seiten oder 35 000 Objekte. Bei rund 135 000 Vorlagen (höchste Kennung in Stufe 1) braucht ein Vollabruf der Vorlagen so zwei Winternächte statt vier, dazu Organisationen und Sitzungen (Umfang unbekannt). `pipeline/abruf.py` kennt keine Grenze für langsame Antworten; die Zeitüberschreitung je Anfrage bleibt 90 s. Köln liefert die Vorlagen neueste zuerst und ohne Gesamtzahlen (`pagination` nur `elementsPerPage` und `currentPage`, Stufe 1): Neue Vorlagen zwischen zwei Nächten verschieben die Seiten nach hinten; in einer Fortsetzung gelten Seiten ohne neue Kennungen bis zu einer Verschiebung von 100 Vorlagen je angefangenem Tag seit dem Speichern der Fortsetzung (`gespeichert`, höchstens 1000; `verschiebung_erlaubt`), aufgerundet auf Seiten (bei 100 je Seite eine je Tag, bei 25 vier; genauer bis zu 99 neue Vorlagen je Tag, weil die wiederholte Seite mitzählt) als Seitenverschiebung, nicht als Schleife; bricht eine Fortsetzung ab, bevor sie die verschobene Zone verlassen hat (noch keine ungelesene Vorlage, deren `created` nicht jünger ist als das der g-ältesten gelesenen, g = tatsächliche Seitengröße, also eine Seite; gleich alt genügt, bis zu g − 1 Platzhalterdaten unter den gelesenen stören nicht), bleibt `gespeichert` (die Verschiebung seit dann besteht weiter). Das setzt voraus, dass Köln die Liste streng nach `created` absteigend sortiert; belegt ist das für die ersten 100 Vorlagen (Stufe 2), über mehrere Seiten noch nicht. Trifft es nicht zu, gilt die Zone zu früh als verlassen (in der Folgenacht womöglich ein Listenfehler) oder nie (erlaubte Verschiebung bis 1000 Vorlagen, ein schwächerer Schutz gegen Schleifen); eine Seite, deren Kennungen alle schon in diesem Lauf kamen, und eine wiederholte Adresse bleiben eine Schleife. Die Fortsetzung beginnt eine Seite vor der Abbruchstelle (eine Anfrage mehr, zählt als Verschiebung): So gehen bis zu einer Seite (bei 100 je Seite 100) zwischen den Nächten gelöschter Vorlagen nicht zulasten der folgenden; bei mehr Löschungen können Vorlagen bis zum nächsten Vollabruf fehlen. Zwischen den Nächten gelöschte, schon gelesene Vorlagen bleiben bis zum nächsten Vollabruf bzw. bis zu ihrem Eintrag mit `deleted` aus `modified_since` im Stand. Doppelungen werden über die Kennung zusammengeführt, die neuen Vorlagen am Listenanfang holt der nächste inkrementelle Lauf; ab dem zweiten vollständigen Lauf `modified_since` mit einem Tag Überlappung (`RATSATLAS_VOLLABRUF=ja` erzwingt einen Vollabruf). Ein Vollabruf ersetzt den Stand nur, wenn er mindestens 90 % der bisherigen Objekte enthält. `pipeline/net.py` (aus Bonn: Wiederholungen, mehrere Verbindungen, kein Zeitfenster) verweigert Anfragen an Adressen der Stadt (stadt-koeln.de, offenedaten-koeln.de, Host der OParl-API), auch als Ziel einer Weiterleitung (ein unlesbares Ziel gilt vorsichtshalber als Adresse der Stadt); solche Abrufe, etwa `fetch-besetzung`, gehören auf `pipeline/abruf.py` umgestellt. Module, die direkt über urllib abrufen (`geodaten.py`, `ebenen.py`, `kontext.py` u. a.), erfasst dieser Schutz nicht.

Runde 18: Ohne Kontakt (`RATSATLAS_KONTAKT`) lehnt der Abruf ein Ziel, das kein lokaler Testserver ist, vor der ersten Anfrage (auch der des Bodys) als Einstellungsfehler ab (ValueError, `abruf_fehler` in `STAND.json`, keine Nacht mit möglicher Sperre), denn der User-Agent muss den Kontakt nennen; lokale Testserver laufen ohne. Eine gespeicherte Fortsetzung gilt nur dann als veraltet und wird verworfen, wenn schon ihre erste Seite HTTP 404 oder 410 liefert (`sessionnet.VERALTET_HTTP`); bei 401, 403 und anderen Codes bleiben Fortsetzung und Teildatei für die nächste Nacht, 401 und 403 zählen wie bisher als Nacht mit möglicher Sperre. Antworten werden mit `json.loads(…, strict=False)` gelesen: rohe Steuerzeichen in Zeichenketten (etwa \x0b in einem Titel) machen eine Seite nicht unlesbar, ungültiges UTF-8 und kein JSON bleiben unlesbar (Wiederholungen, dann `aufgegeben`).

Nebenlisten (Sitzungen, Organisationen; Runde 17): Ihre Warnungen stehen in `STAND.json` unter `abruf_warnungen` je Liste (`zeit`, `meldung` mit Abhilfe), nicht in `abruf_hinweis`; sie werden beim Auftreten vermerkt, ein späterer Abbruch einer anderen Liste und ein vollständiger Lauf lassen sie stehen, entfernt wird die Warnung einer Liste erst, wenn diese Liste wieder regulär aktualisiert wurde. `export` übernimmt gültige Warnungen (nicht vor der letzten regulären Aktualisierung der Liste) in `index.json` (`meta.abruf_warnungen`, mit dem Stand der Liste); die Seite zeigt sie im Datenstand in einfacher Sprache („Sitzungstermine wurden beim letzten Abruf nicht aktualisiert; gezeigt wird der Stand vom …“, ebenso für die Liste der Gremien). Alle Daten im Datenstand (Abrufdatum der Quellen wie „Ratsinformationssystem: …“, „erzeugt …“, „Stand vom …“ und „Der letzte Abruf am …“) folgen einer Regel: Datum des vollen Zeitstempels in Europe/Berlin (23:30 UTC ist dort schon der nächste Tag; ein Zeitstempel ohne Zone gilt als UTC, damit das Datum nicht von der Zone des Rechners abhängt); ist nur der Anfang lesbar, die ersten zehn Zeichen, sonst „unbekannt“. Nach derselben Regel entsteht der Datenstand für die Markierung in der Zeitleiste und die Jahresgrenze der Vorgangs-Feeds (`dataStand`, Berliner Kalendertag), nur aus einem lesbaren Wert: Abruf des Ratsinformationssystems, sonst `generated_at`, sonst heute; die Pipeline bildet die Jahresgrenze der Feeds je Vorlage ebenso (`export.feed_grenze` über `export.berliner_tag`: 1. Januar des Vorjahres des Berliner Kalendertags von `retrieved_at`, unlesbar heute in Berlin), sodass ein Abruf am 31.12. um 23:30 UTC in Pipeline und Seite zum Jahr 2027 zählt (Runde 17e); ein unlesbarer Wert (Text, Zahl, Objekt) bringt die Seite nicht zum Absturz, und `#stand` wird vor der Zeitleiste gesetzt. Wendet der Server `modified_since` bei den Sitzungen nicht an, vermerkt der Zustand den Befund (`meetings_ohne_zeitfilter` mit Zeitpunkt); in den Folgenächten wird die inkrementelle Sitzungsliste ohne Anfrage übersprungen (letzter gültiger Stand, Warnung bleibt, Zeile `übersprungen` in der Abrufstatistik), denn die Zahl der Seiten vor dem Befund wüchse sonst jede Nacht, und das Gelesene wird ohnehin verworfen. Zurückgesetzt wird der Vermerk durch einen vollständigen Abruf der Sitzungen (Abhilfe: ein Lauf mit `RATSATLAS_VOLLABRUF=meetings`, liest nur sie vollständig; eine Fortsetzung zählt mit, auch in einer Folgenacht ohne die Einstellung; `=ja` liest alle Listen vollständig und erreicht die Sitzungen erst nach dem fertigen Vollabruf der Vorlagen, bei rund 135 000 Vorlagen also erst nach mehreren Nächten) oder indem man den Schlüssel `meetings_ohne_zeitfilter` aus `data/raw/zustand_abruf.json` entfernt (dann prüft der nächste Lauf den Zeitfilter erneut, mit Anfragen bis zum Befund). Ist ein Vollabruf einer Liste kürzer als 90 % des Stands und stimmt das (etwa weniger Gremien nach einer Wahlperiode), nimmt ein Lauf mit `RATSATLAS_KUERZER_ANNEHMEN=organizations` (Komma-Liste aus `organizations`, `papers`, `meetings`) den kürzeren Stand an (einen Vollabruf ohne Objekte nie, auch keinen nur mit gelöschten Objekten; Abbruch `leer` wie ohne die Einstellung), mit Warnung im Log und Vermerk in der Abrufstatistik (`ok; kürzerer Stand angenommen …`). Die Einstellung ist ausdrücklich und nur für diesen einen Lauf zu setzen, nie als Vorgabe; danach gilt die 90-%-Regel gegenüber dem neuen Stand. Die 90-%-Prüfung der abgeleiteten Beratungen entfällt nur, wenn für `papers` oder `meetings` tatsächlich ein kürzerer Stand angenommen wurde, nicht schon, weil die Liste in der Einstellung steht (auch nicht nach einem angenommenen kürzeren Stand der Organisationen); bricht der Lauf danach vor den Beratungen ab (etwa am Ende des Zeitfensters), hält der Zustand das fest (`beratungen_kuerzer_erlaubt` mit Zeit und Listen), sodass die nächste Nacht, die die Beratungen erreicht, sie auch ohne die Einstellung ableitet; entfernt wird der Vermerk erst nach dem Schreiben von `beratungen.jsonl`, und einen leeren Beratungsstand (0 bei bisher über 0) nimmt der Abruf nie an. Unbekannte Listen in `RATSATLAS_KUERZER_ANNEHMEN` oder `RATSATLAS_VOLLABRUF` (außer `ja`) lehnt der Abruf vor der ersten Anfrage als Einstellungsfehler ab. Offen: ob Köln `modified_since` bei `meetings` anwendet (ungemessen; vor der Freigabe des nächtlichen Abrufs eine Anfrage); eine Antwort HTTP 401 auf einen Zeitfilter zählt heute als Nacht mit möglicher Sperre (Art `http`, nicht umgebaut); Entscheidungen des Auftraggebers offen: Organisationen mit Abbruch `leer` nur als Warnung, und „älteste zuerst“ gilt in `_filter_urteil` (explore) als nach `created` sortiert; `RATSATLAS_VOLLABRUF` als Komma-Liste und `RATSATLAS_KUERZER_ANNEHMEN` brauchen seine Freigabe; ob die 90-%-Prüfung eines Vollabrufs nur nicht gelöschte Objekte zählen soll (heute zählt sie alle gelieferten, nur „nie 0 Objekte“ zählt die nicht gelöschten); welche Abhilfe es für Beratungen unter 90 % gibt, wenn weder `papers` noch `meetings` kürzer angenommen wurde (heute jede Nacht Abbruch `leer`; `RATSATLAS_KUERZER_ANNEHMEN` hilft nur, wenn die Vorlagen oder Sitzungen selbst kürzer sind). Offen (Entscheidung des Auftraggebers, nicht umgebaut): Endet ein fortgesetzter Vollabruf der Vorlagen oder Sitzungen mit `leer` (unter 90 % des Stands, ohne `RATSATLAS_KUERZER_ANNEHMEN`), bleiben Fortsetzung und Teildatei stehen, und jede Folgenacht liest erneut bis zum Listenende; zu entscheiden ist, ob die Fortsetzung dann verworfen und wie ein Listenfehler gezählt wird oder ob die Liste ohne Anfrage aussetzt, bis die Einstellung gesetzt oder der Zustand geprüft ist. Offen (Workflow nicht geändert): In GitHub Actions reicht `pages.yml` `RATSATLAS_VOLLABRUF` und `RATSATLAS_KUERZER_ANNEHMEN` nicht an den Abrufschritt durch, beide wirken dort also nicht; vor der Freigabe des nächtlichen Abrufs als Eingaben von `workflow_dispatch` vorsehen (leer als Vorgabe, nur im manuellen Lauf), nicht als Repository-Variable (sie gälte sonst jede Nacht). Ebenfalls offen: `#stand` (Datenstand mit Warnungen und fehlgeschlagenem Abruf) liegt in der eingeklappten Legende „Quellen, Lizenzen und Datenstand“, auf Telefonbreite im verborgenen `map-sheet`; ein Hinweis außerhalb wäre später zu erwägen.

### Geokodierung (CLAUDE.md 5.2)

| Methode | Ebene | Konfidenz |
|---|---|---|
| `oparl_sublocality` (Stufe A; auch der Stadtteil eines Punkts aus der Ortsangabe einer Vorlage ohne Erlaubnis für Hauskoordinaten) | Stadtteil | mittel |
| `oparl_location` (Stufe A, Punkt aus der Ortsangabe der Stadt; nur bei Vorlagen mit Erlaubnis für Hauskoordinaten) | Straße | hoch |
| `strasse`, `strasse+ortsteil`, `strasse+bezirk`, `strasse+kreuzung`, `strasse_mehrdeutig` | Straße (ohne Erlaubnis für Hauskoordinaten und bei einer Straße, die nur aus einer Ortsangabe der Stadt bekannt ist: Stadtteil) | mittel bzw. niedrig |
| `strasse+hausnummer` (Stadtteil aus „Adressen Köln“) | Straße | mittel |
| `strasse+hausnummer_punkt` (nur Verwaltungsvorlagen und politische Anträge, `hausnummer_punkt_erlaubt`) | Adresse | hoch |
| `ortsteil_name`, `ortsteil_teilname`, `stadtbezirk_name` (nur eindeutige Bezirksformen) | Stadtteil, Stadtbezirk | mittel |
| `district_from_committee` (nur eine Bezirksvertretung, sonst kein Ort) | Stadtbezirk | niedrig |
| `vererbt` (Ortsbezüge der übergeordneten Vorlage; ohne Erlaubnis für Hauskoordinaten statt der Hauskoordinate der Straßenabschnitt) | wie die übergeordnete Vorlage | höchstens mittel |

Hauskoordinate nur bei erkennbarer Vorlagenart (Entscheidung 10.11.2026): `geocode.VORLAGENART_PUNKT` erkennt Verwaltungsvorlagen und politische Anträge und Anfragen (Kölner Arten aus Stufe 1 und 2, Bonner bzw. übliche SessionNet-Arten, Groß- und Kleinschreibung egal; Eingaben und Einwohneranfragen gehen vor); bei leerer, nicht erkennbarer oder nicht als Text gelieferter Vorlagenart bleibt es wie bei Eingaben beim Straßenabschnitt (`strasse+hausnummer`), und wie bei Eingaben gilt das für alle verbundenen Vorlagen (über- und untergeordnet und `relatedPaper`; vorsichtige Auslegung), in `build` und `check.erlaubnis` gleich. Arten mit „Bürger“ (außer „Bürgermeister“), „Einwohner“, „Anwohner“, „privat“, „Bauantrag“ oder „Bauvoranfrage“ gelten nie als erkannt. Abgeglichen wird ein Vergleichstext (`geocode._vergleichstexte`, auch für Eingaben und Gremien): Unicode NFKC, ohne weiche Trennzeichen und Zeichen ohne Breite, kleingeschrieben, „Paragraf 24“ wie „§ 24“, dazu dieselbe Fassung mit „ae/oe/ue“ als „ä/ö/ü“ („Buergerantrag“); ein Ausschluss gilt bei einem Treffer in einer der beiden Fassungen, eine Erkennung nur bei Treffern in beiden. Gibt es eine Drucksache mehrfach, verliert jede Vorlage mit der Drucksache einer gesperrten Vorlage ebenfalls die Hauskoordinate (`geocode.sperrmenge`), weil `vorlagen.geojson` und die Gebietsdateien Vorlagen unter ihrer Drucksache führen und `check.erlaubnis` dort jede Vorlage dieser Drucksache prüft; der Aufbau urteilt so wie die Prüfung, statt die Veröffentlichung mit einem Befund anzuhalten (seit Runde 19b als Fixpunkt, siehe unten). Die nicht erkannten und die erkannten Arten stehen mit Anzahl im Log von `build` und in der Ausgabe von `check` („Vorlagenart nicht erkennbar …“, „Vorlagenart erkannt, Hauskoordinate möglich …“, nur die Art), damit das Muster nach dem Vollabruf in beide Richtungen geprüft und ergänzt werden kann; die Zeile „Ohne Erlaubnis für Hauskoordinaten“ zählt Gründe, verbundene Vorlagen und Vorlagen mit derselben Drucksache. Die Hausnummer im Titel blendet `maske.py` weiter nur bei Eingaben, Einwohneranfragen, Bauordnung und Naturschutz aus.

Menge ohne Hauskoordinate als Fixpunkt (Runde 19b, Prüfung r19): `geocode.sperrmenge` ist die eine Funktion für `build` (`build._ohne_hauskoordinate`) und `check.erlaubnis`. Startmenge sind die Vorlagen mit Grund aus `geocode.punkt_ausschluss` und die ausgelassenen Vorlagen; danach kommen abwechselnd die verbundenen Vorlagen (über- und untergeordnet und `relatedPaper`, in beiden Richtungen) und die Vorlagen mit derselben Drucksache hinzu, bis nichts mehr hinzukommt. Gerechnet wird das als eine Breitensuche in Schichten in linearer Zeit (Nachbarn und Vorlagen je Drucksache einmal aufgestellt, jede Drucksache einmal; Prüfung r19b: vorher je Wechsel zwischen Beziehung und Drucksache ein Durchlauf über alle Vorlagen, laut Messung der Prüfung brauchte eine erfundene Kette aus 1600 Vorlagen neben 135 000 weiteren 48 s je Aufruf); Menge und Wege sind dieselben wie beim früheren Ablauf in Runden (Test mit zufälligen Beständen). Vorher galt die Drucksache nur einen Schritt weit: Eine Kopie mit derselben Drucksache wie eine Eingabe erbte den Punkt ihrer übergeordneten Vorlage (`check` hielt die Veröffentlichung mit Exit 1 an), und eine mit der Kopie verbundene Vorlage behielt Hauskoordinate und Anschrift als Ortsname, ohne dass `check` es bemerkte. Dazu:
- `relatedPaper` steht in der Tabelle `paper_related` (auch bei ausgelassenen Vorlagen) und zählt für den Datenschutz wie eine Beziehung; `paper_relation`, der Export, `maske.aus_db` und `volltext.einwohner_kette` bleiben ohne `relatedPaper`. Das Log von `build` nennt die Zahl der Vorlagen mit `relatedPaper` und der Vorlagen, die nur darüber gesperrt sind („relatedPaper: … ohne Hauskoordinate nur über relatedPaper: …“), damit sich die Wirkung nach dem Vollabruf ablesen lässt. Im synthetischen Bestand der Prüfung (134 940 Vorlagen, zufällige `relatedPaper`) sperrte das Feld zusätzlich 29 898 Vorlagen; ob und wie Köln es füllt, ist ungemessen.
- Grund „Titel ohne Hausnummer“ (`maske.titel_ohne_hausnummer`, mit denselben Angaben wie `maske.aus_db`: Art und Titel aus der Einwohnerschaft, darunter „Einwohner“ im Titel, oder Bauordnungsamt bzw. Untere Naturschutzbehörde federführend nach dem Namen der Organisation aus `underDirectionOf`): Neben einem Titel, dessen Hausnummer ausgeblendet ist, steht keine Anschrift als Ortsname mit Hauskoordinate. Damit liegt jede Vorlage, deren Titel `maske.py` kürzt, in der Menge ohne Hauskoordinate. Offen (Prüfung r19b, Entscheidung des Auftraggebers): Der Auftrag verlangte das nur für Bauordnung und Naturschutz (`maske.AMT_PRIVAT`); praktisch kommt das Wort „Einwohner“ im Titel einer erkannten Verwaltungsvorlage oder eines Antrags hinzu („Einwohnerversammlung …“, „… für 1200 Einwohnerinnen und Einwohner“), samt den damit verbundenen Vorlagen. Bis zur Entscheidung gilt die vorsichtigere Regel; das Log von `build` zeigt nach dem Vollabruf, was sie kostet („„Einwohner“ im Titel einer erkannten Vorlage …: n Vorlagen; ohne Hauskoordinate nur darüber: k Vorlagen“). Die andere Möglichkeit wäre, für diese Vorlagen statt des Punkts den Ortsnamen im Export zu kürzen.
- `build._inherited`: Eine gesperrte Vorlage erbt nie eine Hauskoordinate, sondern den Straßenabschnitt derselben Straße im Stadtteil der Hausnummer (wie die Rückfallstufe in Stufe B; Fundstelle „übergeordnete Vorlage … (Straßenabschnitt ohne Hausnummer)“), kennt das Straßenverzeichnis die Straße dort nicht, entfällt dieser Ortsbezug. Mit dem Fixpunkt ist die übergeordnete Vorlage einer gesperrten Vorlage selbst gesperrt; die Regel sichert das zusätzlich ab.
- Stufe A: Liefert die Ortsangabe einer gesperrten Vorlage einen Punkt (`geojson` Point), gilt er nur für seinen Stadtteil (Stadtteilfläche wie bei `subLocality`, Methode `oparl_sublocality`; Straße ohne Hausnummer bleibt als Name), außerhalb der Stadtteile ohne Koordinate. Das gilt auch für andere Vorlagen mit derselben Ortsangabe (vorsichtige Auslegung), auch wenn die gesperrte Vorlage beim Aufbau ausgelassen ist (Kennungen ihrer Ortsangaben in `skipped_location`; Prüfung r19b), und solche Ortsangaben liefern keinen Straßenpunkt für das Straßenverzeichnis.
- Stufe B und Volltext (Prüfung r19b): Eine Straße, die das Straßenverzeichnis nicht kennt, kennt der Gazetteer nur aus dem Punkt der Ortsangabe einer erlaubten Vorlage (Quelle `oparl-koeln`); dieser Punkt ist oft eine Anschrift. Für eine gesperrte Vorlage gilt eine solche Straße nur als Stadtteil des Punkts (`build._stadtteil_statt_stadtpunkt`: Ebene Stadtteil, Methode bleibt, Fundstelle „… (Straße nur aus einer Ortsangabe der Stadt bekannt: Stadtteil)“). Vorher stand eine Eingabe, die die Straße mit Hausnummer nennt, auf dem Punkt, den die Stadt für die Anschrift angibt.
- `check`: meldet genaue Punkte aus Ortsangaben der Stadt bei Vorlagen ohne Erlaubnis (Datenbank: jeder Ort der Quelle `oparl-koeln` mit Koordinate auf Ebene „strasse“, aus der eigenen Ortsangabe, vererbt oder aus Stufe B; `vorlagen.geojson` und Gebietsdateien: Methode `oparl_location` oder `location_source` bzw. `source` `oparl-koeln` mit Koordinate, in den Gebietsdateien auf Ebene „strasse“, in `vorlagen.geojson` ohne Ebene außer Stadtteil und vererbten Orten) und genaue Punkte auf einer Ortsangabe, die auch eine ausgelassene Vorlage nennt (`skipped_location`) und prüft unter Punkt 2 neben den Titeln auch die Ortsnamen (`place` in `vorlagen.geojson`, `locations[].name` in den Gebietsdateien) auf Hausnummern.
Geprüft in `tests/test_datenschutz_fixpunkt.py` (erfundene Fälle, Fehler im Aufbau, die `check` meldet, veränderte Exportdateien).

|---|---|---|
| `pages.yml` | täglich 22:10 UTC, bei Push auf `main`, auf Knopfdruck | Abruf (gesperrt bis zur Repository-Variable `RATSATLAS_STADT_INFORMIERT=ja`), Aufbereitung, Export, Datenpaket; Branch `deploy` (Hauptadresse über Plesk) und Spiegel auf GitHub Pages mit Canonical auf `SITE_URL`. | `kacheln.yml` | vierteljährlich, auf Knopfdruck, bei Pull Requests zu `pipeline/kacheln/` | graue Kartenkacheln aus OSM (Protomaps-Ausschnitt Köln) in den Branch `kacheln`, danach `pages.yml` |

Variablen (Einstellungen → Secrets and variables → Actions → Variables): `RATSATLAS_STADT_INFORMIERT`, `RATSATLAS_KONTAKT`, `SITE_URL`; bei Bedarf die Abhilfen aus den Hinweisen des Abrufs, `RATSATLAS_VOLLABRUF` (`ja` oder Listen wie `meetings`) und `RATSATLAS_KUERZER_ANNEHMEN` (Listen wie `organizations`), nur so lange wie nötig: `ja` und `RATSATLAS_KUERZER_ANNEHMEN` für eine Nacht (sonst jede Nacht ein Vollabruf der Vorlagen, rund 900 Anfragen), `meetings` auch dauerhaft, wenn die Stadt `modified_since` bei den Sitzungen übergeht oder ablehnt (jede Nacht alle Sitzungen, 50–200 Seiten); der Zustand des Abrufs liegt im Zwischenspeicher des Workflows, ein Lauf an anderer Stelle wirkt nicht. Abstand, Zeitfenster, Seitengröße und Grenzen je Nacht sind nicht über Variablen einstellbar. Branch `deploy`: flacher Klon, ein Commit je Lauf, die Historie wächst um die Änderungen (Plesk-Git räumt mit `git gc` auf); ohne Datenpaket und, weil GitHub höchstens 100 MB je Datei annimmt (Generalprobe: `audit_prozess.tsv` 98,3 MB; die Audits liegen seit Runde 19 nur im Datenpaket, siehe unten), ohne jede Datei über 95 MB (95 000 000 Byte): Sie bleibt mit `::warning::` (Pfad, Größe) im Log draußen, liegt im Datenpaket und auf dem Spiegel GitHub Pages, und der Push läuft weiter (auf der Hauptadresse fehlt die Datei dann).

Datenpaket und Audits (Runde 19, Entscheidung 10.11.2026): Audit-Protokolle, Stichproben und die Abrufstatistik (`audit_*.tsv` und `stichprobe_*.tsv` in jedem Ordner unter `data/export/`, etwa `hausnummern/stichprobe_hausnummern.tsv`, dazu `abrufstatistik.tsv`) kommen nicht als lose Dateien auf die Seite: `tools/seite_bauen.py` lässt sie beim Kopieren von `data/export/` nach `_site/` aus (`NUR_IM_PAKET`; ein Ordner, der dadurch leer bliebe, entfällt). Sie fehlen damit im Branch `deploy` und auf dem Spiegel. Das Datenpaket entsteht in `pages.yml` vorher (`python -m pipeline package`, `pipeline/paket.py`) aus ganz `data/export/` und enthält sie weiter; auf dem Spiegel liegt es als `data/export/ratsatlas-koeln-export.zip`, im Branch `deploy` verweist der Link per `sed` dorthin (`config.PAKET_URL`). Andere TSV-Dateien unter `data/export/` (etwa `koeln/kurzfassungen.tsv`, nur mit Freigabe `kurzfassungen`) bleiben auf der Seite. Mit Testdaten (`tools/testdaten.py`, 300 Vorlagen) wird `_site` um die 9 Dateien (0,60 MB) kleiner, von 25,61 auf 25,01 MB; mit den Kölner Daten entfällt vor allem `audit_prozess.tsv` (Generalprobe 98,3 MB). Geprüft in `tests/test_datenpaket_freigaben.py` (Bau mit dem lokalen Testserver: keine dieser Dateien in `_site`, alle im Zip, keine inneren Links darauf, Linkprüfung ohne Befund; Reihenfolge `package` vor `seite_bauen.py` vor dem Branch `deploy`). Ohne Freigabe `chat` lässt `tools/seite_bauen.py` außerdem den Ordner `chat/` aus `site/` weg (Module und Bonner Systemprompt des Ratsassistenten, `ORDNER_MIT_FREIGABE`); `app.js` lädt ihn nur über die Schaltfläche des Assistenten, die ohne Freigabe verborgen bleibt.
