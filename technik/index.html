Ratsatlas Köln Zur Karte

So funktioniert der Ratsatlas

Woher kommen die Daten des Ratsatlas, was passiert mit ihnen und wann wird die Seite neu erzeugt? Vier Grafiken zeigen es, vom Überblick bis zur Technik. Sie entstehen aus dem Code im Repository und zeigen den Aufbau, nicht den Verlauf einzelner Läufe.

Auf dieser Seite: Überblick · Datenfluss · Zeitplan · Technik · Grenzen

Überblick

Die Karte erfindet nichts: Sie holt öffentliche Daten der Stadt Köln, ordnet sie jede Nacht neu und zeigt sie so, dass man sie nach Ort, Zeit und Zuständigkeit finden kann. Was die Karte selbst erschließt, etwa den Ort einer Vorlage, ist als abgeleitet gekennzeichnet.

Alle Kästen erklärt
  • Ratsinformationssystem der Stadt: Hier stehen alle öffentlichen Vorlagen, Sitzungen und Gremien. Die Stadt stellt sie über eine offene Schnittstelle bereit.
  • Karten und Flächen: Stadtteile, Stadtbezirke, Straßen und Adressen der Stadt; der Kartenhintergrund aus OpenStreetMap.
  • Abholen: Ein Programm holt geänderte Daten jede Nacht schonend ab; bei einem Ausfall bleibt der letzte Stand.
  • Verorten: Es sucht in Titeln nach Straßen, Stadtteilen und Stadtbezirken und markiert, wie sicher ein Ort ist.
  • Ordnen: Es ordnet Beratungen zu einer Prozesslinie, ermittelt den Stand und ordnet Themen zu.
  • Karte und Liste: Vorlagen auf der Karte und in einer Liste, mit Filtern und Zeitleiste.
  • Gebietsseiten: Eine Seite je Stadtteil und Stadtbezirk, auch ohne Skript lesbar.
  • Feeds und Kalender: Neues abonnieren, Sitzungen im eigenen Kalender.
  • Offene Daten: Alles zum Herunterladen und Weiterverwenden.
  • Bürger:innen: Sehen, was in der eigenen Nachbarschaft beraten wird, und mitwirken.
  • Politik und Verwaltung: Vorgänge und Zuständigkeiten schneller finden.
  • Presse und Initiativen: Verfahren verfolgen und belegen, mit Link zum Original.
  • Weiterverwendung: Apps, Forschung und andere Seiten nutzen die offenen Daten.

Datenfluss

Jeder Kasten in der Mitte ist ein Schritt der Pipeline, aufgerufen mit python -m pipeline <schritt>, in der Reihenfolge des Hauptlaufs. Links stehen die Quellen mit ihrer Lizenz, rechts die Ergebnisse. Die Liste der Schritte liest diese Seite aus dem Workflow; kommt ein Schritt hinzu, erscheint er hier.

Alle Kästen erklärt
  • Ratsinformationssystem: Die OParl-Schnittstelle der Stadt Köln: Vorlagen, Gremien, Sitzungen und Tagesordnungspunkte. Hauptquelle der Karte. Lizenz: dl-de/zero 2.0 laut Katalog „OParl API Koeln“ (Klärung offen, CLAUDE.md 8); Datenquelle: Stadt Köln – offenedaten-koeln.de. Quelle
  • Stadtteile und Stadtbezirke: Flächen der 86 Stadtteile und 9 Stadtbezirke aus dem Open-Data-Portal der Stadt. Lizenz: dl-de/zero 2.0 (Stadt Köln, Stadtteile und Stadtbezirke); Datenquelle: Stadt Köln – offenedaten-koeln.de. Quelle
  • Straßen: Straßen der Stadt Köln; daraus entsteht das Straßenverzeichnis je Stadtteil. Lizenz: dl-de/zero 2.0 (Stadt Köln, Straßen Köln); Datenquelle: Stadt Köln – offenedaten-koeln.de. Quelle
  • Adressen: Adressen der Stadt Köln: Stadtteil einer Hausnummer und, nur bei Vorlagen der Verwaltung und politischen Anträgen, die Hauskoordinate. Lizenz: dl-de/zero 2.0 (Stadt Köln, Adressen Köln); Datenquelle: Stadt Köln – offenedaten-koeln.de. Quelle
  • Bebauungspläne: Flächen der rechtsverbindlichen Bebauungspläne aus der Schnittstelle „Bauleitplanung in NRW“ des Landes; Vorlagen mit Plannummer im Titel erscheinen auf der Fläche des Plans. Lizenz: dl-de/by 2.0 (Bauleitplanung in NRW, INSPIRE: MHKBD NRW / IT.NRW, Datengrundlage Stadt Köln). Quelle
  • OpenStreetMap: Daten der grauen Karte. Lizenz: ODbL 1.0, © OpenStreetMap-Mitwirkende (Kartenhintergrund über Protomaps). Quelle
  • Abruf: Holt Vorlagen, Gremien und Sitzungen mit ihren Tagesordnungspunkten über die OParl-Schnittstelle der Stadt Köln: nachts, mit einer Verbindung und Abstand zwischen den Anfragen, nach dem ersten Lauf nur Geänderte. Bricht ein Abruf ab, bleibt der Stand des letzten Laufs. Code (pipeline/sessionnet.py)
  • Datenbank und Verortung: Baut eine SQLite-Datenbank aus Vorlagen, Beratungen, Sitzungen und Gremien, verortet Vorlagen nach festen Regeln und leitet den Stand jedes Vorgangs ab. Code (pipeline/build.py)
  • Export: Schreibt je Gebiet eine Datei für die Karte, dazu Feeds, Kalender, GeoJSON und Prüfprotokolle. Code (pipeline/export.py)
  • Kennzahlen: Rechnet Kennzahlen je Stadtteil aus Zensus, Bodenrichtwerten, Klimaanalyse, Kitas, Schulen und Haltestellen (Land und Bund) und legt zuschaltbare Flächen und Punkte für die Karte ab. Code (pipeline/kontext.py)
  • Ebenen: Bereitet weitere offene Daten für die Karte auf, etwa Förderprogramme, Wohnbaupotenziale, Schutzgebiete und Hochwassergefahr, mit Quelle und Lizenz je Ebene. Code (pipeline/ebenen.py)
  • Prüfung: Prüft vor jeder Veröffentlichung den Datenschutz (keine Hauskoordinaten bei Eingaben nach § 24 GO NRW und Vorlagen von Privatpersonen) und die Kennzahlen; ein Befund hält die Veröffentlichung an. Code (pipeline/check.py)
  • Datenpaket: Packt Daten, Prüfprotokolle und Lizenzen in ein Zip-Paket zum Herunterladen. Code (pipeline/paket.py)
  • Karte und Liste: Je Gebiet eine JSON-Datei, die die Karte im Browser lädt; die Suche über ganz Köln hat eine eigene Datei. Öffnen
  • Statische Seiten: Gebietsseiten, Begriffe, Feeds und diese Seite, ohne Skript lesbar. Öffnen
  • Feeds und Kalender: Atom-Feeds je Gebiet, je Vorlage und für ganz Köln, dazu ein Sitzungskalender (ICS). Öffnen
  • Offene Daten: GeoJSON der verorteten Vorlagen, Beschreibung nach DCAT-AP und Prüfprotokolle als TSV.
  • Datenpaket: Alle Daten, Prüfprotokolle und Lizenzen als Zip-Paket. Öffnen
  • GitHub Pages: Der Spiegel der Seite unter daimpad.github.io. Öffnen
  • Hauptadresse: Der Branch deploy enthält die fertige Seite; der Server von koeln.ratsatlas.de übernimmt ihn über einen Webhook. Öffnen

Zeitplan

Die Läufe starten von selbst zu festen Zeiten (Cron-Aufträge in GitHub Actions). Die Zeiten sind in UTC angegeben; in Köln ist es eine Stunde später, im Sommer zwei. Abgerufen wird nur nachts zwischen 23 und 1 Uhr.

Alle Kästen erklärt
  • Kartenkacheln: am 7. Januar, April, Juli, Oktober um 03:23 UTC (in Köln 04:23 Uhr, im Sommer 05:23 Uhr). Auslöser: am 7. Januar, April, Juli, Oktober um 03:23 UTC, bei jedem Pull Request, auf Knopfdruck. Erzeugt vierteljährlich die grauen Kartenkacheln für Köln aus OpenStreetMap-Daten und legt sie im Branch kacheln ab. Workflow kacheln.yml
  • Hauptlauf: täglich 22:10 UTC (in Köln 23:10 Uhr, im Sommer 00:10 Uhr). Auslöser: täglich 22:10 UTC, bei jeder Änderung an main, auf Knopfdruck. Holt die Daten, bereitet sie auf und veröffentlicht die Seite: auf GitHub Pages und im Branch deploy, aus dem der Server der Hauptadresse liest. Ohne Daten der Stadt veröffentlicht er nichts. Workflow pages.yml
  • Kartenkacheln: am 7. Januar, April, Juli, Oktober um 03:23 UTC. Erzeugt vierteljährlich die grauen Kartenkacheln für Köln aus OpenStreetMap-Daten und legt sie im Branch kacheln ab. Workflow kacheln.yml
  • Live-Prüfung: Auslöser: auf Knopfdruck. Prüft, ob Hauptadresse und Spiegel den neuen Stand zeigen und wichtige Seiten und Feeds antworten. Workflow live.yml
  • Tests: Auslöser: bei jeder Änderung an main, bei jedem Pull Request. Prüft jede Änderung am Code mit Tests gegen einen lokalen Testserver, ohne Anfragen an die Stadt. Workflow tests.yml

Technik

Die Karte braucht keinen eigenen Rechner, der ständig läuft: Ein Python-Programm erzeugt jede Nacht fertige Dateien, die ein einfacher Webserver ausliefert. Im Browser zeichnet Leaflet die Karte. Tests prüfen jede Änderung, bevor sie veröffentlicht wird.

Alle Kästen erklärt
  • GitHub Actions: 4 Workflows steuern Abruf, Prüfung und Veröffentlichung (Grafik „Zeitplan“). Läufe auf GitHub
  • GitHub Pages: Hostet den Spiegel der Seite. Spiegel
  • Webhosting (Plesk): Der Server der Hauptadresse übernimmt den Branch deploy über einen Webhook; .htaccess setzt Sicherheitskopfzeilen. Hauptadresse
  • Branches: Neben main: deploy, kacheln. Sie halten die fertige Seite und die Kartenkacheln getrennt vom Code. Branches
  • HTML und CSS: Statische Seiten ohne Server-Programm; Glas-Stil, WCAG 2.1 AA.
  • JavaScript: Eigener Code ohne Framework für Karte, Liste, Zeitleiste und Tour. Code (site/app.js)
  • Leaflet 1.9.4: Bibliothek für die Karte, mit Markercluster; lokal eingebunden, ohne fremde Server. Leaflet
  • Graue Kacheln: Kartenhintergrund vom eigenen Server, erzeugt aus OpenStreetMap-Daten; „Farbige Karte“ lädt Kacheln von OpenStreetMap. Code
  • pytest: 15 Dateien mit Tests für Abruf, Aufbereitung, Verortung und Export, gegen einen lokalen Testserver. Tests
  • axe-core: Prüft die Barrierefreiheit (WCAG 2.1 A und AA) der Seite. Prüfskript
  • Python 3.12: Die Pipeline in python -m pipeline, ein Schritt je Aufgabe (Grafik „Datenfluss“). Code
  • SQLite: Datenbank eines Laufs; sie wird nicht veröffentlicht, nur ihre Exporte. Code
  • shapely: Python-Paket aus requirements.txt: Geometrie, etwa ob ein Punkt in einem Stadtteil liegt PyPI
  • pyproj: Python-Paket aus requirements.txt: Umrechnung zwischen Koordinatensystemen (ETRS89/UTM 32N nach WGS84) PyPI
  • pyshp: Python-Paket aus requirements.txt: Lesen der Shapefiles der Stadt Köln PyPI
  • cairosvg: Python-Paket aus requirements.txt: Bild der Themenseite als PNG zum Teilen PyPI
  • OParl (JSON): Offener Standard für Ratsinformationssysteme; die Stadt Köln bietet ihn an. OParl
  • Shapefile: Format der Kölner Geodaten (Stadtteile, Straßen, Adressen).
  • GeoJSON: Flächen für die Seite und die verorteten Vorlagen.

Grenzen

  • Diese Seite zeigt den Aufbau. Ob ein Lauf gelungen ist, zeigt GitHub: Läufe der Workflows.
  • Einmalige Schritte, etwa das Ableiten der Geodaten (python -m pipeline geo-koeln), laufen nicht automatisch und fehlen im Zeitplan.
  • Der Server der Hauptadresse übernimmt den Branch deploy von sich aus; sein Zeitpunkt steht nicht im Repository.
